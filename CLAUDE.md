# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Algorender is a Next.js 16 app for learning algorithms and data structures visually, and is being rebuilt into a broader platform (DS&A → math → ML → systems). `REVAMP_PLAN.md` at the repo root is the plan: read its roadmap and decisions before proposing architecture. Every visualiser now runs on the trace engine (one dynamic route, `app/(detail)/visualisers/[slug]`); there are no legacy per-page visualisers left. Other routes: `/` (Today; a stub until the redesign's phase 3), `/explore` (the catalogue of every visualiser; old `/?tab=` links redirect to `/explore?kind=`), `/learn` (concept map with mastery, lessons, and `/learn/placement`, the placement check), `/plan` (the study plan), `/play` (games, XP, levels and badges), `/design` (system-design case studies on the simulator, `/design/sandbox` and `/design/estimate` drills), `/code` (exercises), `/practice` (interview-style problems, judged in the browser in Python/JS/TS and on the server in Java/C++/Go), `/review` (the daily spaced-review queue), `/account` (sign in, sync), `/api/auth/*`, `/api/progress`, `/api/judge`, `/api/tutor` and `/api/explain` (the only server routes; `/search-index.json` is a static file built from content), `/compare` (sorting race + growth chart), `/embed/[slug]` (chrome-less iframe embeds), `sitemap.xml`, `robots.txt`.

## Development Commands

Run everything from `algorender/`:

```bash
npm run dev          # dev server on localhost:3000
npm run build        # production build (also type-checks)
npm run lint         # ESLint (flat config, eslint.config.mjs)
npm run typecheck    # tsc --noEmit
npm test             # Vitest unit + property tests (src/**/*.test.ts)
npm run e2e          # Playwright (e2e/); reuses a dev server on E2E_PORT (default 3100), else starts `npm run dev`
npm run workers      # bundle the JS runner's worker (runs before dev and build; add -- --watch while editing src/workspace/js)
npm run db:generate  # write a migration into drizzle/ after changing src/server/db/schema.ts
npm run db:migrate   # apply drizzle/ to the Postgres in DATABASE_URL (PGlite migrates itself)
npm run models       # retrain the pretrained models in src/ml/pretrained/ (deterministic; commit the JSON)
npm run judge:image  # build the local server judge (Docker image algorender-judge: g++, JDK 21, Go)
node --no-warnings scripts/stubs.mjs two-sum java   # a problem's generated starter code (any language, or all)
PROBLEMS=two-sum,min-stack npx vitest run src/server/judge/solutions.test.ts   # Java/C++/Go reference solutions in Docker (JUDGE_SOLUTIONS=1: all)
```

The user's global `~/.npmrc` sets `os=linux`, which makes npm skip Windows native binaries (Tailwind's oxide, lightningcss, Next's SWC). Run installs with `npm_config_os=win32` set in the environment; don't add that to a project `.npmrc` (Vercel builds on Linux).

The full e2e suite (~330 tests, including axe scans of every page in both themes) is heavy next to `next dev`. On a low-memory machine, run it against a production build instead: `npm run build`, then `BETTER_AUTH_RATE_LIMIT=off PGLITE_DIR=<a fresh folder> npx next start -p 3100` (the account tests sign up many learners from one address, and the offline test needs the production service worker), then `npm run e2e -- --workers=1`. Playwright reuses whatever already listens on the port, so stop any stale server first.

**Environment:** nothing is needed locally: the database is PGlite in `.data/pglite` (git-ignored) and auth uses a development secret. On Vercel set `DATABASE_URL` (any Postgres, e.g. Neon; run `npm run db:migrate` against it first) and `BETTER_AUTH_SECRET`; optionally `BETTER_AUTH_URL` and `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` for those sign-in buttons. The server judge (Java, C++, Go) uses Docker locally when the `algorender-judge` image exists (`npm run judge:image`; without it those languages answer "not set up"); on Vercel it needs `JUDGE_SNAPSHOT_ID` from `node --env-file=.env.local scripts/judge-snapshot.mjs` (run once, after `vercel env pull`), and optionally `JUDGE_RUNS_PER_HOUR`/`JUDGE_RUNS_PER_DAY` (30/200). `JUDGE_SANDBOX=docker|vercel|off` overrides the choice. The AI tutor is off unless `AZURE_AI_ENDPOINT` (an Azure AI Foundry resource's OpenAI v1 base URL, `https://<resource>.openai.azure.com/openai/v1`) and `AZURE_AI_API_KEY` are set; then `TUTOR_MODEL_FAST`/`TUTOR_MODEL_STRONG` name the deployments (default `gpt-6-luna`, `gpt-6.1-sol`), `TUTOR_PRICE_FAST`/`TUTOR_PRICE_STRONG` give "input,output" dollars per million tokens, `TUTOR_TURNS_PER_DAY` (30) and `TUTOR_DAILY_USD` (5) set the limits, and `TUTOR_ENABLED=off` is the kill switch. Pages read the switch at build time, so redeploy after changing it, and run `npm run db:migrate` first (the `tutor_turn` table). Locally, `TUTOR_PROVIDER=fake` answers from a stand-in model (refused on Vercel); `e2e/tutor.spec.ts` needs it and skips without. Explain-it-back scoring (`/api/explain`) runs on the same settings and budgets.

## Architecture

### Trace engine (record → replay): how all new visualisers work

1. Each step is a `Frame` (`src/engine/types.ts`): a state snapshot, the pseudo-code `line`, a one-sentence `note` (narration that says *why*), `vars`, running `stats`, and optionally a `checkpoint` (a Predict-mode question about the *next* frame; the frame's own note must not reveal the answer).
2. Two module kinds (`src/engine/module.ts`):
   - **`AlgorithmModule<I, S>`** (`defineAlgorithm`): a pure generator `run(input)` over an `InputSpec<I>` (named examples taking `{seed, size}`, an optional size slider, optional custom text with `parse`/`format`). Lives in `src/algorithms/<family>/<slug>.ts`.
   - **`StructureModule<M, S>`** (`defineStructure`): an immutable model `M` changed by operations (`run(model, args)` is a generator that yields frames and **returns the new model**; it must never mutate `model`). Lives in `src/structures/<family>/<slug>.ts`. The explorer keeps history/undo and encodes operations in the URL (`?start=&seed=&ops=push:5;pop`).
3. Each module names a `view` kind; `src/viz/views.tsx` maps kinds to renderers (`array`, `grid`, `graph`, `tree`, `linear`, `hash`, `text`, `memory` for learner code run line by line, and `plot` for math and ML). A view gets `{ state }` and owns its tracer/types under `src/viz/<kind>/`. `ArrayTracer` (`src/viz/array/tracer.ts`) is the reference pattern: mutate through methods, `t.frame({...})` returns a copy-on-write snapshot.
4. `recordTrace()` / `recordOperation()` (`src/engine/trace.ts`) record a run; `useTracePlayer()` holds only an index on a requestAnimationFrame clock (step back, scrub, `?step=` deep links), and gates forward motion on unanswered Predict questions.
5. Views key every element by **stable id** and animate with Motion (`layout`/`layoutId` for HTML, `motion.*` SVG elements animating attributes). Motion components inherit the stage's `MotionConfig` (tween length from playback speed; `reducedMotion="user"`).
6. `src/registry.ts` merges the per-family registries (`src/algorithms/<family>/index.ts`, `src/structures/<family>/index.ts`); `app/visualisers/[slug]/page.tsx` serves every registered module. `src/components/explorer/` holds the shared UI: `TraceStage` (view, narration, predict card, controls, pseudo-code, stats, variables, legend), `AlgorithmExplorer`, `StructureExplorer`, `InputPanel`.

**Porting a visualiser:** write the module (generator, pseudo-code, stats, legend with a `{ neutral: … }` row, `content` with idea/invariant/whenToUse/traits/experiments, checkpoints at real decisions), add it to its family's `index.ts`, delete the legacy `app/visualisers/<slug>/` folder (static folders take precedence over `[slug]`), and add property tests next to it (correct result vs a reference implementation on random inputs, every frame narrated, valid pseudo-code lines, well-formed checkpoints, monotonic stats, and for structures: operations never mutate their input model).

**Never** animate by mutating React state inside async loops with sleeps, and never key moving elements by array index: that is what made the legacy pages choppy.

**Reuse a view before writing one.** `GridView` (`src/viz/grid/types.ts`) composes parts: tables (look `table`/`board`/`timeline`, cell styles incl. `block` walls, arrows, pieces, interval `bars`, `guides`, per-row `scales`, a `group` to sit parts side by side), lists and meters. `TreeView` (`src/viz/tree/types.ts`) draws one tree or a forest (`roots`, `parentArrows`, an aligned `table` of rows, sibling `links` such as a B+ tree's leaf chain), and with `search: true` a recursion/decision tree; build those from a list of calls with `src/viz/tree/search.ts`, which lays out the whole tree up front so nodes never move as it is revealed and turns sideways on narrow screens.

**Math and ML (`PlotView`, direct manipulation):**
- `PlotView` (`src/viz/plot/`) draws coordinate planes side by side (`equal: true` keeps units square; `false` is a chart box) plus matrix and readout panels. Shapes are in world coordinates and keyed by id: `vector`, `point`, `path` (curves, trails, filled polygons), `line` (infinite, clipped), `label`, `bars` (histograms and distributions; pair them with named `Axis.ticks` for categories), and `contours` (marching squares, `contours.ts`; compute a contour map once per input and share it across frames, since the view memoises on it). `warp: Mat2` draws the integer grid moved by a matrix. Besides planes, a state can hold `image` parts (grayscale or signed pixels, beside the planes), `network` parts (`NetworkView.tsx`: value boxes, op circles and neurons with arrows; a signed edge `weight` sets width and hue; place nodes with `layered`/`depthColumns` in `network.ts`), `bits` parts (a bit row split into toned fields, full width) and `tokens` parts (a wrapping row of token chips on top, keyed by id so merges and new tokens glide; spaces show as ·). Images take `boxes` (outlines that glide: a convolution window, a cache's new row), `values` (text per pixel, for small grids) and `size`. `heatmap` shapes wash a plane with decision regions (`regionHeatmap` in `src/ml/datasets.ts`), or with `scale: { kind: 'intensity' }` tint a weight matrix strongly enough to read (attention). A shape's `tone` outranks its `mark` when painting, so give a marked shape no tone. Plane coordinates are rounded to hundredths, because `Math.tanh`/`Math.exp` differ in the last bit between Node and the browser and trained models would otherwise break hydration.
- **ML code (`src/ml/`):** `autograd.ts` is a micrograd-style scalar `Value` engine (each op records its local derivatives at forward time; `backward()` walks reverse topological order), the reference the chain-rule visualiser narrates and the "build micrograd" exercises (`src/content/exercises/ml.ts`) mirror. `mlp.ts` trains small tanh networks fast on plain arrays, and its gradients are tested against the engine. `datasets.ts` has seeded 2D datasets inside `DATA_BOX`. Models too slow to train on page load are trained at build time: `npm run models` (`scripts/train-models.mjs` bundles `src/ml/train/index.ts` with esbuild and runs each trainer deterministically) writes compact JSON to `src/ml/pretrained/`, which is committed; `pretrained.test.ts` fails when a trainer's config hash no longer matches its JSON (bump the config's `version` when the training code changes) and checks the model's quality. The first is the diffusion denoiser (`denoiser.ts`). Every module ships on every visualiser page (`Visualiser.tsx` imports the registry), so keep pretrained JSON small. Colour is a mark (a state) or a `tone` (a named series: î and ĵ, one optimizer each; `TONES` in `marks.ts`, legend rows `{ tone, label }`). Tones fall below 3:1 on light surfaces, so anything toned carries a text label.
- Plot modules rebuild their parts each frame with `plotFrame()` and ask with `ask()` (sorted choices) or `askInOrder()` (`src/viz/plot/frame.ts`); there is no tracer. Test them with `expectGoodPlotTrace` (`src/viz/plot/testing.ts`).
- **Dragged input:** a plane's `handles` can be dragged or moved with the arrow keys (Shift: four steps), snapping to `step` inside per-axis `min`/`max`. The module's `input.drag(input, handle, to)` returns the new input; `AlgorithmExplorer` stores it as custom text (so `custom` must round-trip it), records the trace again and keeps the current frame (the stage is not remounted; `live` turns tweens off while dragging, and Predict answers reset with the new trace). Only put a handle where the drawn shape sits at the input's own value (e.g. a column of A only once î has landed there).
- Families: `src/algorithms/linear-algebra/` (linear transformations, eigenvectors, SVD image compression with its own Jacobi SVD), `src/algorithms/calculus/` (derivative, gradient descent, the optimizer race on the shared loss surfaces in `surfaces.ts`), `src/algorithms/probability/` (Bayes as areas, the central limit theorem), `src/algorithms/information/` (entropy, cross-entropy, KL), `src/algorithms/numerics/` (float32 bit layout, with exact stored values via BigInt), `src/algorithms/ml/` (linear and logistic regression, k-means, the perceptron, decision trees, gradient boosting, the MLP playground), `src/algorithms/deep-learning/` (convolution, ReLU and pooling), `src/algorithms/llm/` (BPE, attention with a draggable query, sampling with temperature/top-k/top-p from a toy word model in `corpus.ts`, the KV cache), `src/algorithms/rl/` (tabular Q-learning on gridworlds, with value iteration as the reference) and `src/algorithms/generative/` (2D diffusion with the pretrained denoiser). The chain rule lives with calculus. Their entries in `src/data/visualisers.js` are `type: 'math'` (the home page's "Math & ML" tab) and have no complexities.

**Systems (`src/systems/`, `src/algorithms/systems/`, `src/structures/systems/`):** each simulator keeps its model as a pure, steppable simulation in `src/systems/` (no React, no engine imports, immutable state, seeded randomness), separate from the visualiser module that narrates it, because the system-design canvas (REVAMP_PLAN.md, phase 6d) reuses the models as components. Keep each model's API small and general (a cache's `get`/`put` and hit counts, a queue's rates and latency percentiles). Models: `scheduling.ts` (FCFS, SJF, SRTF, round robin, priority; the `cpu-scheduling` Gantt chart on GridView), `cache.ts` (O(1) LRU and LFU; the `lru-cache` structure), `paging.ts` (FIFO, LRU, OPT, Clock, Bélády's anomaly; `page-replacement`), `ring.ts` (consistent hashing with virtual nodes against mod N; the `consistent-hashing` structure on PlotView), `queueing.ts` (M/M/c discrete-event simulation; `queueing`), `token-bucket.ts` (`token-bucket`), `raft.ts` (a discrete-event Raft cluster with seeded election timeouts, crashes and partitions, property-tested for Raft's safety properties; the `raft` structure, where the learner injects the faults), `clocks.ts` (Lamport and vector clocks over a scenario of local, send and receive events; `logical-clocks`, a space-time diagram on PlotView), `lsm.ts` (memtable, SSTables with Bloom filters, leveled compaction, tombstones, write and read amplification; the `lsm-tree` structure), `bplus-tree.ts` (a B+ tree index with linked leaves, page reads and range scans; the `b-plus-tree` structure on TreeView, whose `links` draw the leaf chain), `interleaving.ts` (threads of atomic instructions, one schedule or every interleaving's outcome; `race-conditions`) and `deadlock.ts` (locks taken by scripted processes, the resource-allocation and wait-for graphs, cycle detection, Coffman's conditions; `deadlock` on GraphView). Their entries in `src/data/visualisers.js` are `type: 'systems'` (the home page's Systems tab), and the concept graph's `systems` track is its own area in placement and next steps.

**Operations:** `disabledReason(model, args?)` blocks an operation with a reason (the form disables itself as the learner types; replay and the run button use `blockedReason()`). Use `type: 'choice'` args (options from the model) for references that must exist. Prefer a narrated run over disabling when the attempt itself teaches (searching for a missing key).

### Lessons and the concept graph

- `src/content/concepts.yaml` (validated by Zod in `concepts.ts`) is the concept graph: tracks, concepts with prerequisites, the visualisers that teach each, an optional lesson, and planned concepts for the roadmap. `src/content/content.test.ts` rejects unknown ids, cycles, untaught visualisers, and planned concepts that link anywhere.
- Lessons are MDX in `src/content/lessons/<slug>.mdx`, listed with their metadata in `src/content/lessons/index.ts`, served by `app/learn/[lesson]`. Every lesson follows the learning loop with `<Section step="hook|parts|see|predict|do|check|explain|recap">`, and uses the widgets registered in `src/mdx-components.tsx`: `Terms`/`Term` (pre-training), `Explore` (a visualiser; `settings` take the same keys as the page URL), `PredictChallenge` (predict mode with a goal; make sure the run has at least that many questions), `Quiz` (retrieval practice with explanations), `KeyIdea`, `Misconception`, `ExplainBack`. Math uses `$…$` (KaTeX).
- **Assessment (`src/content/lessons/assessment.ts`, read from the MDX on the server like the quizzes):**
  - `<Misconception id="…" title="…" probes={[…]}>correction</Misconception>` names a common mistake. Its `probes` are questions that test for it later, each with a `trap` (the choice the mistake leads to); they aren't shown in the lesson. A `<Quiz>` question marks wrong choices that are a mistake with `traps: { <choice>: '<id>' }`. Picking one names the mistake, links to its correction (`#mistake-<id>`) and records `misconception.picked`. Every lesson has at least one mistake, every mistake two probes and a quiz question that traps it (`assessment.test.ts`).
  - `<ExplainBack id prompt rubric example />` (in a `step="explain"` section before the recap) asks for the idea in the learner's own words. A signed-in learner with the tutor on gets it scored point by point by the fast model (`/api/explain`, `src/server/tutor/explain.ts`); otherwise they score themselves against the rubric and the example answer. Either way it records `explanation.scored`; the text stays a local draft.
  - Quiz questions are referenced by index (review cards, placement), so only append new ones; never reorder, insert or remove.
- Visualisers inside lessons run with `variant="lesson"`: they start from their settings, never write the URL, keep keyboard shortcuts to the focused stage, stack their panels, and ask at every decision in Predict mode.
- Progress (completed lessons, best quiz and prediction scores, and each quiz answer, which starts that question in the review queue) is recorded as events through `src/components/lesson/progress.ts` (see Accounts and progress).

### Code workspace (learner code drives the views)

- `src/workspace/protocol.ts` is the contract: a `RunRequest` (language, code, entry function, args, limits) produces a `RunResult` whose `events` (array created, compare, write, append, pop, print — each with the learner's line and simple local `vars`) describe what the code did to its *visual collections*. `src/workspace/contract.ts` holds the shared cases every runtime must pass, with exact events; add a case there when you change semantics, never in one runtime only.
- Learners can make their own visual collections with `table(rows, cols, fill)` and `array(values)` (both runtimes provide them); a `cellWrite` carries `from`, the cells read since the statement began (tracked per call, so memoised recursion and helpers work), which the grid trace draws as dependency arrows. `traceFor()` picks the view: GridView (every collection as a table) once a run makes a grid, otherwise ArrayView.
- `trace.ts` turns events into the same `Trace<ArrayState>` the built-in visualisers play (two writes that exchange two cells on the same or the next line become a swap, keeping element identity, so bars slide). `runner.ts` owns the workers, kills one that overruns its time budget, and starts a fresh one next run.
- **Python** runs in Pyodide 314 (CDN) in `public/workers/python.js`, a classic worker script that loads Pyodide's classic build with `importScripts`. The Python-side logic is `HARNESS` in `python/harness.ts` (AST rewrite of comparisons, `VisualList`, a `sys.settrace` step counter, print capture), sent to the worker on init and unit-tested in Node with the npm `pyodide` build. **JS/TS** is stripped with sucrase, instrumented with acorn/astring and run by `js/runtime.ts`; `scripts/build-workers.mjs` (esbuild) bundles `js/js.worker.ts` into `public/workers/js.js` (generated and git-ignored, so rerun `npm run workers` after changing the runtime while `next dev` runs). The runtime is plain TS, tested directly in Node.
- Exercises live in `src/content/exercises/`: the model in `shared.ts` (task, starter and solution per language, an `args` builder, examples to watch, judged tests, a `check` that explains failures, hints), one file per family (`arrays.ts`, `grids.ts`, `graphs.ts`, `trees.ts`), gathered by `index.ts`. `/code` lists them, `/code/[slug]` hosts `Workspace.tsx`, and a visualiser page links to its exercise. `exercises.test.ts` runs every solution and starter through both runtimes and checks the languages do the same things to the arrays, tables and graphs. Verdicts are local practice feedback, labelled as such.
- **Exercise formats** (`Workspace.tsx` is a ladder of stages; `useExerciseRun` runs whatever code a stage produces against the example and every test, and `RunOutput` shows verdicts and the trace): `parsons` (shuffled solution lines plus `distractors`; Python indentation is part of the puzzle, JS indentation follows the braces; `formats/parsons.ts`), `fill` (the solution with `«n:text»` blanks in `blanks`, and `fades` listing which blanks each level hides; `formats/blanks.ts`), `write` (the editor), and `bug` (kind `'bug'`: the starter has one bug, `bug.symptom`/`bug.explanation`). Kind `'modify'` starts from working code (PRIMM's Modify). Verdicts come from running the tests, so any working answer passes; the reference order and answers only power opt-in hints ("point out a misplaced line", "reveal a gap"). Passed stages are kept in localStorage (`storage.ts`).
- **Line by line (`mode: 'lines'`, Python Tutor style):**
  - **Runtimes:** both also emit a `step` event before every line, at every return, and as an exception unwinds. A step holds the whole stack (Global frame first, locals in binding order, harness names hidden; a Python closure's free variables are drawn in the frame that defines them, as in JS) and the heap reachable from it. Object ids stay stable for the run, so two names for one list share an arrow.
  - **Limits:** `MAX_ITEMS`, `MAX_OBJECTS` and `MAX_DEPTH` cap what a step holds, and runs use `LINE_LIMITS`.
  - **Contract:** lines-mode contract cases compare steps across languages by shape. Primitives are spelled per language, and refs are relabelled by first appearance.
  - **Trace:** `lines.ts` holds the step walker (`traceSteps`, one frame per step, narrated by `narrate`), shared by every view of a 'lines' run; a view adds clauses for what memory can't show. `traceLines()` (picked by `traceFor()` when a run has steps) turns steps into `Trace<MemoryState>`. Changes are flagged by diffing steps, and a note says what the line did. Pass `code` in the options so a condition line is narrated as "Line 2: n <= 1? No, so line 5 is next."
  - **View:** `MemoryView` (`src/viz/memory/`) draws frames, objects and measured SVG arrows. Its screen-reader description is `describe.ts`, and `fixtures.ts` holds sample states.
  - **Workspace:** the "Line by line, with memory" switch runs only the example this way; the tests still run in visual mode.
- **Graphs and trees (learner code on GraphView and TreeView):**
  - **Arguments:** `graph` (each node's neighbours in reading order, `graphArg()` in `exercises/graphs.ts` builds it in label order; a read-only dict / object whose reads are `neighbours` and `edge` events) and `tree` (level order, LeetCode style; the function gets the root `TreeNode`, which is also in scope, and a returned tree comes back in level order). Contract cases cover both.
  - **Watching:** their examples always run in 'lines' mode (`watchedByLine`), and `traceFor()` draws the steps on GraphView (`traceGraph.ts`) or TreeView (`traceTree.ts`); `view: 'memory'` (the "Show the memory diagram" switch) asks for the memory view instead.
  - **Marks come from the learner's own variables, never their names:** in a queue or stack (a list the code takes items out of) or a paused call = waiting; in another set, dict or list = recorded; the node whose neighbours the innermost call reads, or that it took out of a queue into a variable, or its first node-valued variable = current; the edge taken just before a node first appears anywhere = the edge that reached it. Every container gets a panel named after its variable, and the first dict of numbers is written under the nodes. On a tree, the innermost call's most recently assigned tree variable is current, paused calls' nodes wait and draw the path down, and a node the code makes floats as its own root until it is linked in.
- **Lessons** embed code with these widgets:
  - `<PredictCode exercise="…" question choices answer why />`: read the solution, predict, then run. Running is locked until the learner predicts.
  - `<CodeExercise exercise="…" stages={[…]} />`.
  - `<TraceCode snippet="…" />`: a short, editable program run line by line on the memory view. It takes the same optional predict props.
  - Snippets live in `src/content/snippets.ts`, and write Python there rather than in MDX props, where indentation is fragile. `snippets.test.ts` runs every one in every language it offers.
  - Use `exercise="…"` for exercise slugs and `snippet="…"` for snippets; content tests check both. `slug="…"` is for visualisers.
  - Section steps include PRIMM's `run`, `investigate`, `modify` and `make`. `sorting-in-code.mdx` is the PRIMM template; `recursion.mdx` shows tracing.
- **Sandbox** (`runner.ts`, `public/sandbox.html`): learner code never runs with the app's origin.
  - Each runtime's worker lives in a hidden `<iframe sandbox="allow-scripts">`, so it has an opaque origin: it can't read the app's cookies or storage, or call its API as the learner. The frame's CSP lets it fetch only jsDelivr (Pyodide).
  - The page fetches the worker script itself (same-origin, cached) and hands it over as text with a `MessagePort`, then talks to the worker directly on that port. A timeout removes the frame, which kills the worker, and the next run makes a new one.
  - Both workers are classic scripts, because a module worker can't start from a blob in an opaque origin.
  - Server routes must never accept the `null` origin with credentials.
  - In e2e tests, init scripts run in every frame, including the sandbox's, which has no storage: touch `localStorage` only when `window === window.top` (see `useLanguage` in `e2e/workspace.spec.ts`).

### Practice problems (`/practice`, the local judge)

- **Content:** one YAML file per problem in `src/content/problems/<slug>.yaml`, validated by `ProblemSchema` (`src/problems/schema.ts`, which documents every field). Statements, examples, hints and approaches are our own words, never copied from another site.
  - **Signature:** a typed function (`int`, `float`, `bool`, `string`, arrays and 2D arrays of them, `TreeNode`, `ListNode`; a `void` function names its `inPlace` argument), or a `design` class whose tests are call lists, constructor first: `[[MinStack], [push, 3], [getMin]]`. Signatures are camelCase; Python gets snake_case (`codegen.ts`, which also writes every language's stub).
  - **Tests:** `examples` (shown and judged), hand-picked `tests`, and seeded `generated` tests from a generator in `src/content/problems/gen-*.ts`, whose answers come from the TypeScript solution, run on the server at build time (`load.ts`). Keep a problem's tests well under 200 KB: they travel with the page.
  - **Answers** are compared in trusted code (`judge.ts`): `exact`, `float`, `unordered` (top level), `unordered-deep`, or a named `check` in `src/content/problems/checks.ts` for problems with several right answers. An empty tree or list is `[]`.
  - **Solutions:** Python, TypeScript, Java, C++ and Go; JavaScript is the TypeScript with its types stripped. Write the compiled ones from the generated stub (`scripts/stubs.mjs`), with the same algorithm, and check them with `solutions.test.ts` (Docker). `problems.test.ts` loads every problem, runs every stub (which must parse and fail something) and every solution against every test in all three languages through the browser's judge, and replays the examples on their view. `PROBLEMS=a,b npx vitest run src/content/problems` checks just those.
- **Judge mode (`mode: 'judge'` in the protocol):** the code runs as written (TypeScript stripped, no instrumentation, no step counter), so big tests run at full speed and only the worker's timeout stops a loop. Arguments are plain values (trees and lists as `TreeNode`/`ListNode`), printing is capped (`MAX_PRINTS`), an error's line comes from the stack or traceback, and the result carries each argument's final value. Design problems pass `calls`. Contract cases cover all of it.
- **Pages:** `/practice` (grouped by main pattern, or mixed with the patterns hidden; difficulty and solved filters), `/practice/[slug]` (statement beside `ProblemWorkspace`: Run examples, Submit, a chip per test, the selected test's input, expected answer, yours and its prints), `/practice/drills` (name the pattern for a mixed round of statements; wrong options come from `CONFUSED_WITH` in `patterns.ts`).
- **Watching a test:** `watchRequest` replays one test on the problem's `view`: an `int[]` argument line by line on the array view (`traceArray.ts`: a frame per line, the learner's index variables from `POINTERS` drawn under the array, compares and writes marked and narrated), an `int[][]` from its cell reads and writes on the grid, a tree on TreeView, anything else on the memory view, which the learner can always switch to.
- **Progress:** every submission is a `problem.submitted` event (`src/problems/progress.ts`); a first solve starts the problem in the review queue. Code drafts stay in localStorage under `algorender:code:problem:<slug>:<language>`, and the problem language under `algorender:problem-language`.

### The server judge (Java, C++, Go)

- **Languages:** `src/problems/languages.ts` (`ProblemLanguage` = the browser's `Language` plus `ServerLanguage`, labels, `TIME_FACTOR`). Stubs follow LeetCode's conventions: `class Solution` in Java and C++, Go functions with `Constructor()` and exported methods (`methodIn`) for design problems; Java returns lists of lists as `List<List<…>>`.
- **Drivers** (`src/problems/drivers/`, plain functions, unit-tested): `encode.ts` writes the tests as typed tokens on stdin (strings by UTF-8 length, arrays by count, trees in level order); `java.ts`, `cpp.ts`, `go.ts` generate a driver around the learner's code that parses each test first, times only the call, and writes one JSON line per test to `answers.jsonl` (value, error and its line, `x` for a crash), printing a marker line on stdout before each test so prints split by test. Line numbers match the editor: Java's imports share line 1, C++ uses `#line`, Go `//line` (Go code without imports gets common packages imported, with blank uses). Errors: exceptions and panics per test; C++ crashes via a signal handler on its own stack; a 64 MB (Java, Go) or 256 MB (C++) stack. `shared.ts` has `judge.sh` (compile, run under `timeout`, capped files, status line); `index.ts` reads the files back into the same verdicts as the browser (`verdict()`), stopping at a timeout or crash. Expected answers never enter the sandbox.
- **Sandboxes** (`src/server/judge/`): `sandbox.ts` picks one (`JUDGE_SANDBOX`, else Vercel on Vercel, Docker elsewhere); `docker.ts` runs `algorender-judge` (`judge/Dockerfile`) with no network, 2 GB, 2 CPUs, no capabilities; `vercel.ts` makes a Vercel Sandbox microVM per run from `JUDGE_SNAPSHOT_ID`, with `networkPolicy: 'deny-all'`, and stops it after. `index.ts` is the service: request validation, one run at a time and hourly/daily quotas counted in the `judge_run` table, and a submission's verdict written as a `problem.submitted` event with `verified: true` (sync drops that flag from device-sent events; the device keeps the server's copy with `store.receive`).
- **Workspace:** the language picker offers all six; Java/C++/Go need sign-in (`ServerNote`, `SignInCard`, `/account?next=` returns to the problem), send one request per run (`serverJudge.ts`), can't be watched, and show compile errors as a `compile` error at the learner's line.
- **Tests:** `drivers.test.ts` (encoding, reading output), `src/server/judge/judge.test.ts` (every value shape and failure mode through Docker; skipped without the image), `service.test.ts` (quotas, events, on PGlite with a stand-in sandbox), `solutions.test.ts` (every reference solution and stub, opt-in), `vercel.test.ts` (Two Sum through the real Vercel Sandbox, opt-in: `node --env-file=.env.local node_modules/vitest/vitest.mjs run src/server/judge/vercel.test.ts` after `vercel env pull`), `e2e/server-judge.spec.ts`.

### The AI tutor (`src/server/tutor/`, `POST /api/tutor`)

- **Where:** a panel beside practice problems and code exercises (on their own pages, not in lessons): `TutorPanel` (`src/components/tutor/`). Signed-in learners only; signed out it offers sign-in.
- **Models:** Azure AI Foundry through the OpenAI v1 Responses API with plain `fetch` (`model.ts`: `POST <endpoint>/responses`, the deployment as `model`, the key as a bearer token, structured JSON output). The fast model writes hints and runs the leak check; the strong model reviews code. `fakeModel()` stands in for tests.
- **Guardrails, enforced on the server (`index.ts`):**
  - The hint ladder (`src/lib/tutor-ladder.ts`): 1 a nudge, 2 where to look (a line), 3 the steps as pseudo-code, 4 a partial fix. Levels unlock one at a time per item, counted from `tutor_turn` rows, and level 4 only after a failed run and two earlier turns.
  - The first turn on an item, and every review, needs the learner's own account of what is happening. A review needs a hint first and a failed run.
  - Budgets: turns per learner per day, and a global daily spend cap from each turn's recorded cost.
- **Grounding (`prompt.ts`):** the statement, the authors' hints and approach, and the reference solution in the learner's language, which it must never quote. Learner data (code with line numbers, test results, explanation, question, history) sits in `<learner_…>` fences after `defuse()`, so it can't close a fence or pose as instructions.
- **Leak check (`leak.ts`):** a free deterministic check (code lines allowed per level, and the share of the solution's token runs not already in the learner's code), then for level 3+ and reviews a fast-model check. A leaking reply is retried once with a stricter instruction, then replaced, and the turn is marked `leakBlocked`.
- **Panel:** asks "what do you think is happening?" first, names the next level on its button, offers "What will you try?" (sent with the next turn), highlights the line a reply points at (`CodeEditor`'s `pointLine`), and renders replies as Markdown without links or HTML.
- **Explain-it-back scoring (`explain.ts`, `POST /api/explain`):** the fast model gets the prompt, rubric, example answer and the lesson's mistakes, with the learner's text fenced and defused, and answers a verdict per point (yes, partly, no), a quote, feedback and an optional mistake id. The reply is checked (one verdict per point, quotes really in the text, only the lesson's mistake ids). It shares the tutor's budgets and records a `tutor_turn` (`action: 'explain'`, level 0); the explanation is never stored.
- **Tests:** `tutor.test.ts` (ladder, budgets, model routing, leak retry and fallback, prompt defusing, the Azure wire format, settings) and `explain.test.ts` on in-memory PGlite; `e2e/tutor.spec.ts` and the model case in `e2e/assessment.spec.ts` with `TUTOR_PROVIDER=fake`.

### Play (`src/play/`, `/play`)

- **Games** (`src/play/games.ts` lists them; each round is a `game.played` event via `recordGame`, whose `score`/`max`/`won` mean different things per game, documented on the event):
  - **Be the algorithm** (`/play/be-the-algorithm/[slug]`): the learner makes the next swap (two bars, then "Swap these two") or says "No more swaps". `moves.ts` reads the moves from a recorded trace: every change of the main lane's order between frames must be one swap (`movesOf` throws otherwise), so only modules whose array changes by swaps alone are `SUPPORTED` (bubble, selection, quick, heap sort); a move is judged by the value order it makes, so swapping an equal value counts. A wrong move outlines the true pair (`hint`) with the swap frame's note. Bars become buttons through `ArraySelectContext` (`src/viz/array/select.ts`); without it, `ArrayView` renders exactly as before. Rounds use the module's `random` example with `?seed=&size=`.
  - **Comparison budget** (`/play/comparison-budget`): sort hidden cards by comparing pairs, against ⌈log₂ n!⌉, merge sort's and binary insertion's worst cases. The order only counts if the comparisons prove it (`forced`), and an "orders still possible" counter shows the halving. Pure logic in `budget.ts`.
  - **Break it** (`/play/break-it`): quicksort's worst case (run on the real module), a greedy coin-change counterexample, and a `k mod 8` hash flood. Pure checkers in `challenges.ts`.
- **XP, levels, badges and the daily challenge** (`src/progress/play.ts`, a projection like mastery; shown by `PlayHub`): XP only for evidence of learning (right first answers, recall 1, 7 and 30 days after a card was made, first solves, exercise stages, explanations over `EXPLAINED_AT`, cleared mistakes, game moves and wins with `XP.repeats` cutting replays of one item on one day), never for watching, marking done or time. Levels per concept are trace, predict, implement and analyse, reached in any order. Badges are informational and never lost. The daily challenge is due reviews, the next step from `nextSteps`, and a game round. Social play (streaks, leagues, duels) is opt-in and comes later (6e).
- **Tests:** `play.test.ts` (XP rules, levels, badges), `moves.test.ts`, `budget.test.ts`, `challenges.test.ts`; e2e `play-*.spec.ts`, and the Play pages are in `a11y.spec.ts`.

### System design (`src/systems/design/`, `/design`)

- **The contract** is `src/systems/design/types.ts`. A `Design` is a list of components wired by id: one `clients` component (a `Workload`: rate, read share, keys, Zipf skew, an optional spike), and any of a rate limiter, a load balancer, an app tier, a cache cluster, a database (shards × a primary and replicas, lag, failover) and a queue. `Fault`s crash an instance at a time; database nodes are numbered shard by shard, primary first.
- **The simulator** (`simulate.ts`) is a seeded discrete-event simulation, request by request, built on the 6b/6c models. Caches are real `cache.ts` caches (through `openCache`, a live O(1) handle). Keys are placed on cache nodes and shards with `ring.ts`, the limiter is `token-bucket.ts`, and every server is a queue with workers, checked against Erlang C. An app worker is held while it waits downstream, so a slow database shows up as busy app servers. Key versions are tracked, so stale reads (writes that skip the cache, replica lag, queued writes) are counted. Results carry percentiles, 0.5 s buckets, per-instance utilisation, cost (`cost.ts`, published-style prices) and plain-language `findings`. About 10,000 req/s for 10 s simulates in about half a second; keep case studies at about 10 s and ≤ 20,000 req/s.
- **The rest of the engine:** `validate.ts` (wiring rules in `ALLOWED`, `LIMITS` keyed `${kind}.${field}`, shared with the inspector's inputs), `build.ts` (`newComponent`, `KIND_INFO`, `starterDesign`) and `evaluate.ts` (runs a case's workload, then its fault run, and returns `Check`s against its `Targets`, with seed `EVALUATION_SEED`).
- **The canvas** (`src/components/design/`):
  - `DesignCanvas` (`variant` page or lesson) holds the palette, the auto-laid-out `Diagram`, the `Inspector`, the run controls and the `Results`.
  - `Diagram` lays out tiers by longest path (`layout.ts`), so nodes never move when settings change, and nodes are buttons.
  - `Results` includes `LatencyChart`, which has a hidden table.
  - The pure parts are `wiring.ts`, `layout.ts`, `url.ts` and `format.ts` (`canvas.test.ts`).
  - The sandbox keeps the design in `?d=` (base64url JSON); a case keeps it in localStorage under `algorender:design:<slug>`. Lessons keep nothing and record nothing.
- **Case studies** are in `src/content/designs/` (one file each, listed in `index.ts`). Each has a brief, requirements, a fixed workload, targets, a start that fails instructively, a `reference` that passes (`designs.test.ts` checks both), graded hints, and the trade-off it teaches. The slugs `sandbox` and `estimate` are taken by static routes.
- **In lessons:** `<DesignLab preset="…" caption="…" />` embeds the canvas, with presets from `src/content/designs/presets.ts`. The estimation drills are `src/systems/design/estimation.ts` (seeded generators, `parseEstimate` for "300k" or "40 GB", and a log-scale `judge`: within ×2 is spot on, within ×10 the right order). They're used by `<EstimationDrill kind seed />` in lessons and the `/design/estimate` round, are practice only, and aren't recorded.
- **Progress:**
  - Every case run on its page is a `design.checked` event.
  - A pass counts as mastery evidence for the case's concept, once per case per day; failed runs count for nothing, since iterating is the point.
  - The first pass of a case gives `XP.designPassed` and the "Architect" badge, and makes the concept's implement level.

### Accounts and progress (`src/server/`, `src/progress/`)

- **Server:** the only server code. Drizzle over Postgres (`src/server/db/`): `DATABASE_URL` → node-postgres, otherwise PGlite in `PGLITE_DIR` (default `.data/pglite`), migrated on start from `drizzle/`. Better Auth (`src/server/auth.ts`, served by `app/api/auth/[...all]`): email and password, GitHub/Google when keys are set, database sessions, rate limits counted in the database (off with `BETTER_AUTH_RATE_LIMIT=off`, outside Vercel only), and the Origin check forced on everywhere, test runners included. `src/server/providers.ts` says which social buttons exist without loading the database.
- **Progress is an event log** (`src/progress/events.ts`, Zod-validated on both sides): `lesson.completed`, `lesson.scored`, `quiz.answered`, `exercise.passed`, `problem.submitted`, `review.rated`, `placement.answered`, `concept.marked` (the learner says they know a concept; it counts like a right placement answer), `misconception.picked` (an answer that comes from a lesson's common mistake), `explanation.scored` (an explain-it-back answer against its rubric, by the learner or the model), `game.played` (a finished round of a Play game), `design.checked` (a system-design case run against its targets), `plan.set` (a study plan's goal, hours a week and target date; a null goal clears it), each with a UUIDv7 id and the device's time. Never change what an existing kind means; add a kind. Everything else is a pure projection of the events (`projections.ts`, `review.ts`), so devices merge by taking the union.
- **The device store** (`store.ts`): events in IndexedDB (Dexie; memory if unavailable), recorded instantly and synced in the background (`POST /api/progress`: push unsent events idempotently, pull from a cursor; `src/server/progress.ts`). Events have an owner: `anon` until sign-in, which claims them for the account. Explicit sign-out syncs, then removes the account's events from the device; an expired session only hides them. Progress saved before the event log is imported once (`legacy.ts`). `hooks.ts` gives React the snapshot and projections; anything that depends on progress at mount (the exercise ladder) waits for `ready`.
- **Review (FSRS via ts-fsrs, day-based, no fuzz):** a solved problem makes `problem:<slug>` (first review Good, Hard after failed submissions); a quiz question's first answer makes `quiz:<lesson>:<quiz>:<n>` (Good or Again); a common mistake makes `misconception:<lesson>:<id>` (Again, so it is due the next day), which asks the mistake's probes in turn and shows the correction. A mistake clears after `CLEAR_AFTER` right answers in a row (`src/progress/misconceptions.ts`); making it again reopens it and sends the card back to tomorrow. `/review` shows due cards; its card faces are built on the server (`lessonQuizzes()` in `src/content/lessons/quizzes.ts` reads `<Quiz>` questions from the MDX with acorn) and ship with the page. The rail and the phone tab bar show how many are due; `SessionSync` (`src/components/shell/`, mounted by every app layout) tells the store who is signed in.
- **Mastery (`src/progress/mastery.ts`, a projection like review):**
  - **Evidence:** every quiz answer, prediction challenge, exercise pass, problem submission (once per problem, day and outcome) and review rating is evidence about concepts. `masteryGraph()` (`src/content/mastery.ts`, server) maps lessons, exercises (via their visualiser) and problems (via their patterns' `concept`) to concepts and hands the graph to client components as data.
  - **Tracing:** Bayesian knowledge tracing per concept (`BKT`). Statuses are `new`, `learning`, `practised`, `mastered`, `placed` and `assumed`. Mastered needs delayed, varied retrieval: p ≥ 0.95, two distinct items, a right answer `DELAY_HOURS` after first contact, and no open mistake in its lesson. An explanation scoring at least `EXPLAINED_AT` of its rubric counts as a right answer. A known concept makes its untouched prerequisites `assumed`.
  - **Next steps:** `nextSteps()` lists started concepts first, then the fringe (every prerequisite known), spread across the three areas. `toward` limits it to goal concepts and what leads to them.
  - **On the concept map:** `/learn` shows a status on every card (`ConceptStatus`), next steps at the top (`NextSteps`) and the mistakes still to clear (`MistakesToClear`), all in `src/components/learn/Mastery.tsx`.
- **Placement check (`src/progress/placement.ts`, `/learn/placement`):**
  - **Questions:** it asks lesson quiz questions (`placementQuestions()`) about concepts, picking each time the concept that best splits what is still unsettled. A right answer settles its prerequisites as known, a miss settles what builds on it as unknown, and a concept's own answer always wins (`settled()`).
  - **Length:** at most `MAX_QUESTIONS`. An area stops after `AREA_MISSES` misses with nothing right there, and the learner can finish at any time.
  - **Recording:** each answer is a `placement.answered` event. It sets where tracing starts and makes no review card.
  - **Test:** `mastery.test.ts` checks that a learner whose knowledge respects the graph is never settled wrongly.
- **Study plans (`src/progress/plan.ts`, `/plan`, another projection):**
  - **Goals:** `src/content/goals.ts` lists the goals. Each names its target concepts in the order to learn them.
  - **Schedule:** a plan takes the targets plus everything they build on, minus what is known, in prerequisite order. Among ready concepts, the one serving the earliest target comes first. `pack()` fits them into seven-day windows from the day the plan was set, at the chosen hours less `REVIEW_SHARE` for reviews; an item is never split.
  - **Re-planning:** it's automatic. Known concepts drop out and the rest pack from the current window.
  - **Tracking:** "behind" counts concepts the schedule as originally set had due in ended windows that aren't known yet. `hoursNeeded` is the fewest whole hours whose packing meets the target date.
  - **Catalog:** `planCatalog()` (server) gives each concept its time estimate (`effort()`) and where to learn and practise it (lesson, visualisers, problems easiest first, exercises, links). Concepts with nothing to answer can be marked known (`concept.marked`).
- **Offline:** `public/sw.js` (registered in production by `ServiceWorker.tsx`) caches hashed assets for good and pages network-first; `/review` is precached. Playwright blocks service workers except in the offline test.
- **Tests:** `src/server/server.test.ts` (accounts, rate limits, origin checks and sync on in-memory PGlite), `src/progress/store.test.ts` (two devices against the real sync code, offline, sign-out, an expired session), `progress.test.ts` (projections, scheduling, quiz extraction), `e2e/accounts.spec.ts`.

### Design system

State colours are theme tokens in `app/globals.css` (Okabe–Ito, colour-blind-safe): `bar`, `mark-compare`, `mark-swap`, `mark-write`, `mark-focus`, `mark-frontier`, `mark-done`. `src/viz/marks.ts` is the one shared vocabulary (`compare`, `swap`, `write`, `pivot`, `min`, `key`, `frontier`, `sorted`, `visited`, `found`, `path`, `reject`), each with a glyph and `bg`/`fill`/`stroke`/`text` classes, so colour is never the only cue and a colour means the same thing in every view. Modules relabel marks in their legend rather than inventing colours.

**Colours are semantic tokens, never palette classes.** `globals.css` defines what a colour is *for*: planes `page`, `surface`, `subtle`, `sunken`; hairlines `line-soft`, `line`, `line-strong`; text `ink`, `ink-soft`, `ink-muted` (and `ink-faint`, decoration only, below text contrast); `accent`/`accent-strong` (violet, for run, play and progress; text on them is `text-on-accent`, white in light and dark in dark), `accent-ink`, `accent-soft`, `accent-line`; `primary`/`on-primary` (the main action: an ink pill in light, a paper pill in dark); `feature`/`on-feature`/`feature-muted` (dark feature cards); `rail*`, `badge`, `xp`, `code*`, `segment`, `review-page`; feedback `good`/`warn`/`bad` with `-ink` (icons, text), `-title` (titles on the soft fill), `-soft`, `-line`, and `good` is also a fill with `on-good`; `track-{lilac,peach,mint,sky,butter,rose,teal}` with `-ink` and `-title` (one pastel per concept-map track, mapped in `src/data/tracks.ts`, which Learn, Explore, Today and Play all read); `mark-*-ink` for mark hues as text; `series-1..4` for chart series. Write `bg-surface text-ink border-line`, not `bg-white text-gray-900 border-gray-200`; every ink clears 4.5:1 on page, surface and sunken in both themes. Text on a mark *fill* is `text-white` on `compare` and `text-on-mark` (dark in both themes) on every other mark; unmarked text takes the theme's `ink`. Tints of a fill (`bg-mark-done/25`, `opacity-25` overlays) work in both themes.

**Shape, type and primitives (the 2026 redesign, `docs/redesign/`, kept local).** Radii are `rounded-card` (32), `rounded-tile` (24), `rounded-well` (18) and pills; cards have no border or shadow (depth is page → surface → well), and the only shadow is `shadow-segment`. Bricolage Grotesque is `font-display`, with the sizes `text-title-page`, `text-title-section`, `text-title-card`, `text-number-big`, `text-number-tile` and `text-eyebrow` (add `uppercase`). Build screens from `src/components/ui/`: `Button`/`ButtonLink`/`IconButton` (kinds primary, accent, secondary, soft, ghost, danger, onTrack), `Card`/`TrackCard`/`TrackCardLink`/`FeatureCard`, `SectionTabs`, `Segmented`, `Chip`/`DifficultyChip`/`MonoTag`/`StatusChip` (`displayStatus()` maps a mastery status to the six shown), `CountTile`/`BigNumber`/`ProgressBar`, `Alert`, `Field`/`SelectField`, `CodeBlock`/`Kbd` and `BottomSheet`. They use `clsx`, not `cn`: tailwind-merge doesn't know the custom text sizes and would drop a colour next to one. `/dev/ui` shows them all (unlinked, not indexed); `e2e/redesign.spec.ts` screenshots finished routes at 1440 and 390 in both themes into `test-results/redesign/`. Every interactive element gets the global 3px accent focus ring.

**Dark mode** redefines the tokens, so components need no `dark:` variants. It follows the OS by default; the rail's `ThemeToggle` (System → Light → Dark) stamps `data-theme` on `<html>`, saved in localStorage and applied before paint by `THEME_SCRIPT` (`src/lib/theme.ts`), and an embed can pass `?theme=light|dark`. The custom `dark:` variant covers both the OS and the stamp, for the rare one-off (the home-page gradient). Mark fills are the same in both themes (see the note in `globals.css` on why they sit above the dataviz dark lightness band). Colours that end up in style props (chart series) are `var(--color-…)` strings, set via `style`, not SVG attributes.

**Accessibility conventions:** a view's panels are `role="group"` with a label, not `<section>` landmarks or headings (a page can hold several visualisers, and panel titles don't belong in its outline). Narration is a polite live region while stepping and silent during playback. Keyboard-readable charts are sliders with `aria-valuetext`. `html` has `scroll-padding-top` so anchors and focus clear the sticky header, and `prefers-reduced-motion` stops CSS tweens as well as Motion's.
