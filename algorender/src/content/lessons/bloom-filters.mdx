<Section step="hook" title="Have I seen this one before?">

A web crawler has fetched a billion pages, and each holds more links. Before following one it asks: have I been here
already? A [hash set](/learn/hash-tables) of every URL would answer exactly, but it keeps every URL in full: at 60
characters each, 60 GB before any overhead.

A **Bloom filter** answers in about 10 bits per URL, 1.25 GB for the billion, and keeps no URLs at all. It pays in
certainty, but only in one direction: "definitely not" is always true, while "probably present" is now and then wrong,
which costs the crawler the odd page it never fetched.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="bit array">m bits, numbered 0 to m − 1, all 0 at the start. They are everything the filter keeps: no items, no keys.</Term>
  <Term name="hash functions">k different functions that each turn an item into a bit position, hᵢ(x) mod m. The same item always gets the same k positions, and two of them can land on the same bit.</Term>
  <Term name="add">Switch on the item's k bits. A bit that is already 1 stays 1.</Term>
  <Term name="test">Look at the same k bits. Any 0 means "definitely not"; all 1s means "probably present".</Term>
  <Term name="false positive">"Probably present" for an item that was never added, because other items happened to switch on all of its bits. The opposite mistake, a false negative, can't happen.</Term>
</Terms>

</Section>

<Section step="see" title="Switch bits on, then look at them">

This filter has m = 16 bits and k = 3 hash functions: the polynomial hash from the hash table lesson, with three
different bases, 31, 37 and 41. Base 31 turns “cat” into 98262, the number the hash table used; bases 37 and 41 give
139236 and 170512. Mod 16, those pick bits 6, 4 and 0.

<Explore slug="bloom-filter" settings={{ start: 'empty' }} caption="Add “cat”, then “dog”. “cat” switches on bits 6, 4 and 0. “dog” picks bits 12, 6 and 2; bit 6 is already on, set by “cat”, so only two bits change." />

Words share bits, and nothing records which word switched a bit on. (The demo lists the words added only to flag
mistakes; a real filter keeps no list.) A test looks at the same positions.

<Explore slug="bloom-filter" settings={{ start: 'example' }} caption="This filter holds “cat”, “dog” and “owl”. Test “cat”: bits 6, 4 and 0 are all on, so the answer is probably present. Then test “cow”: it picks bits 11, 13 and 1, and the first of them, bit 11, is 0. That one bit settles it: definitely not." />

A 0 is proof: had “cow” been added, bit 11 would be 1, so the test stops at the first 0. All 1s proves much less:
every added word looks like that, but so does a word whose bits others switched on.

<KeyIdea>

**Adding an item switches on its k bits, and no bit is ever switched off, so an added item always tests "probably
present": a Bloom filter has no false negatives. A 0 among an item's bits proves it was never added; all 1s only says
that nothing rules it out.** Add and test each compute k hashes and touch k bits: O(k), however many items the filter
holds.

</KeyIdea>

The more a filter holds, the more bits are on, and the more often a word never added finds all of its bits on by
chance.

<Explore slug="bloom-filter" settings={{ start: 'crowded' }} caption="This filter holds 8 words, and 13 of its 16 bits are on. Test “hen”, which was never added: its bits 1, 15 and 3 were switched on by “yak” and “emu”, so the filter says probably present, a false positive. The panel at the bottom puts the expected rate for 8 words at 46.9%." />

That 46.9% comes from a short calculation. After n adds, a given bit is still 0 with a chance of about $e^{-kn/m}$, so
a word that was never added finds all k of its bits on with a chance of about $(1 - e^{-kn/m})^k$: 8.0% for this
filter with three words, 46.9% with eight. Real filters have millions of bits, but fill up the same way.

</Section>

<Section step="do" title="A filter in code, and what it can't do">

Here is a whole Bloom filter: 10 bits and two hash functions. Real hashes mix every letter; to keep this one easy to
follow, each reads one letter: `positions` returns the last digit of the first letter's code and the last digit of the
last letter's code. Codes run from 97 for a to 122 for z, so c (99) picks bit 9, t (116) bit 6, d (100) bit 0, g (103)
bit 3 and b (98) bit 8. The program adds “cat” and “dog”, then tests “cab” and “cog”.

A Bloom filter earns its place in front of something slow: "definitely not" skips the slow step, and a wrong
"probably" must be cheap, either because an exact check follows or because acting on it costs little.

- An [LSM tree](/learn/storage-engines) keeps a filter in memory for each table on disk and reads only the tables whose
  filter says "probably": a false positive wastes one read.
- A crawler skips links its filter has seen: a false positive skips one unfetched page.
- A [cache](/learn/caching) can store an object only on its second request, with a filter remembering first requests,
  so one-off requests never push out popular ones.

"Probably present" only means that none of the item's bits is 0, and other items can switch all of them on. The filter
can't tell that from a real match, because it never kept the items. Treat "probably" as "worth checking". Where a wrong
yes would do harm, such as banning an account, a Bloom filter must never have the last word.

</Misconception>

The same design explains what a filter can't do. It can't list its items: it never kept them. It can't grow: hᵢ(x)
mod m changes with m, and with no items there is nothing to rehash, so an overfull filter is rebuilt from the original
data. And it can't delete, though the obvious way to try looks harmless.

>

Clearing an item's bits erases parts of other items. With “cat”, “dog” and “owl” added, owl's bits are 4, 6 and 10,
but bit 6 is also cat's and dog's, and bit 4 is cat's. Clear them and “cat” and “dog” both test "definitely not": false
negatives, the one mistake a filter must never make. A **counting Bloom filter** keeps a small counter (usually 4 bits)
at each position: add increments the item's k counters, delete decrements them (safe only for items really added), and
a test looks for zeros, at several times the memory. A plain filter is rebuilt without the item.

</Misconception>

Sizing a filter means choosing m/n, the bits per item, and k. The best k is about (m/n) ln 2, roughly 0.69 × m/n,
which leaves half the bits on once the filter is full. Then 9.6 bits per item give 1% false positives (with 7 hash
functions), and each further 4.8 bits per item divides the rate by ten. The items' size doesn't matter: a 2 KB
document costs the same 9.6 bits as a three-letter word.

</Misconception>

<Section step="recap" title="What to remember">

- A Bloom filter is m bits and k hash functions. Add switches on an item's k bits and test looks at them: both O(k),
  however many items it holds, and no items are stored.
- "Definitely not" is always true, because bits are never switched off. "Probably present" can be a false positive.
- The false-positive rate, about $(1 - e^{-kn/m})^k$, rises as the filter fills. With the best k, about 0.69 × m/n,
  9.6 bits per item give 1%.
- It can't list, delete or grow: clearing bits erases parts of other items, and growing needs the items it never kept.
- Use it as a cheap check in front of something expensive, never alone where a wrong yes is unacceptable. A hash set
  is exact.
- Next: [storage engines](/learn/storage-engines), where every table of an LSM tree sits behind a Bloom filter.
  [Spot a Repeated Number](/practice/contains-duplicate) and
  [Longest Run of Consecutive Values](/practice/longest-consecutive-sequence) need exact answers to "seen it?", so they
  call for a hash set, not a filter. Open [the Bloom filter visualiser](/visualisers/bloom-filter) to test your own words.

</Section>
