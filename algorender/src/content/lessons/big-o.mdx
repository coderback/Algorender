<Section step="hook" title="Which one is faster?">

You need to find a name in a sorted list of 1,000. One way checks each name in turn: up to 1,000 looks. Another opens the
list in the middle, sees which half the name is in, and repeats: at most 10 looks. Make the list a million names long and
the first way needs up to a million looks, the second about 20.

A stopwatch can't settle which is faster: it depends on the machine, the language and the list you happened to try. What
doesn't change is **how the number of steps grows as the input grows**. Big-O is the name for that growth.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="n">The size of the input: the items in a list, the nodes in a graph, the characters in a string.</Term>
  <Term name="step">One basic operation the algorithm repeats, such as a comparison, a swap or a probe. We count these, not seconds.</Term>
  <Term name="growth">How the step count changes as n grows. The quickest test: double n and see what happens to the count.</Term>
  <Term name="O(f(n))">For large enough n, the steps are at most a constant times f(n). Constant factors and smaller terms are dropped.</Term>
  <Term name="worst case">The input of size n that takes the most steps. A Big-O without a qualifier usually means this one.</Term>
</Terms>

</Section>

<Section step="see" title="Watch two sorts pull apart">

Bubble sort compares neighbours and swaps them, pass after pass. Merge sort splits the list in halves, sorts each half
and merges them. Here is how many comparisons each makes on random lists as n goes from 4 to 64.

  example="random"
  stat="comparisons"
  label="Comparisons"
  max={64}
  step={4}
  curves={['n²/2', 'n log₂ n']}
  caption="Each point is a real run on a random list. Move along the chart, or use the arrow keys, to read the counts at any n."
/>

At n = 8 the two are close. At n = 64, bubble sort makes about 2,000 comparisons and merge sort about 310. Now try the
doubling test: from n = 32 to n = 64, bubble sort's count goes up about **four times**, and merge sort's only a little
more than **twice**. Bubble sort compares about every pair, roughly n²/2 of them, so it is O(n²). Merge sort
does about n comparisons on each of log₂ n levels of halving, so it is O(n log n).

<KeyIdea>

**Big-O keeps only the term that wins as n grows, and drops constant factors.** An algorithm taking 3n² + 50n + 1,000
steps is O(n²): at n = 10,000 the n² term is 300,000,000 and the rest is about 500,000. Whatever the constants, an
O(n log n) algorithm beats an O(n²) one once n is large enough.

</KeyIdea>

The classes you will meet most, from slowest-growing to fastest:

- **O(1)**, constant: the same steps whatever n is, like reading A[i].
- **O(log n)**, logarithmic: the problem halves every step, as in binary search. A million values take about 20 steps.
- **O(n)**, linear: each item is looked at once, as in linear search or adding up a list.
- **O(n log n)**: halve the problem, then do O(n) work at each of the log n levels, as merge sort does.
- **O(n²)**, quadratic: every pair, as in bubble sort or two loops nested over the same list.

</Section>

<Section step="do" title="Test a claim: linear against binary search">

Linear search checks each value in turn; binary search halves a sorted array with every probe. Both look for a value that
isn't there, the worst case for each.

Linear search's line is the n line itself: double n and its probes double. Binary search's barely rises: doubling n adds

Big-O drops constant factors because they don't change how the work **grows**: 2n and n both double when n doubles, so

different question from Big-O's. Write O(n), never O(2n).

can beat an O(n log n) one on small inputs, because constant factors decide there. What Big-O promises is who wins as n
gets large, and that promise is the one that matters when inputs grow.

      trap: 0,
      why: 'Nesting multiplies, but the inner work is a binary search, O(log n), not a full loop. n times log n is O(n log n).',

Count what each loop does, and how they are arranged. Loops **one after another** add: O(n) + O(n) is still O(n). Loops
**nested** multiply: n repetitions of O(n) work is O(n²), but n repetitions of an O(log n) search is O(n log n).

</Misconception>

<Section step="recap" title="What to remember">

- Count **steps** as a function of n, not seconds. Big-O names how that count grows.
- Keep the fastest-growing term and drop constants: 3n² + 50n is O(n²).
- The doubling test: constant stays put, O(log n) adds one step, O(n) doubles, O(n log n) a bit more than doubles, O(n²)
  quadruples.
- Loops one after another add; loops nested inside each other multiply.
- Next: **recursion**, where counting the calls in the call tree gives the Big-O, and **arrays**, where O(1) indexing and
  O(n) inserts come from. To race more sorts against each other, open [the sorting race](/compare).

</Section>
