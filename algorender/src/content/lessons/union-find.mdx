<Section step="hook" title="Can these two reach each other yet?">

A building is being wired one cable at a time, each cable joining two computers. After every cable someone asks: can
computer 3 now reach computer 8 through any chain of cables? Searching from 3 each time walks the cables laid so far,
again and again.

It is really a question about groups. Computers that can reach each other form a group, and a new cable can only merge
two groups, or do nothing if its ends already share one. **Union-find** tracks exactly that. It answers "same group?"
and merges groups in nearly constant time, averaged over many operations, using just two [arrays](/learn/arrays) of
numbers.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="disjoint sets">Groups that share no elements, so every element is in exactly one set. Union-find is also called a disjoint-set structure.</Term>
  <Term name="parent and root">Each element stores one number, parent[x]. Following parents from any element ends at the root of its set, the one element that is its own parent. The root names the set.</Term>
  <Term name="find and connected">find(x) climbs parent links from x to the root and returns it. connected(a, b) asks whether find(a) and find(b) are the same root.</Term>
  <Term name="union">union(a, b) merges the set holding a with the set holding b: it finds both roots and makes one the parent of the other.</Term>
  <Term name="rank and path compression">Two tricks that keep trees flat. A root's rank is an upper bound on its tree's height, and union by rank hangs the root of lower rank under the other. Path compression points every element a find climbs past straight at the root.</Term>
</Terms>

</Section>

<Section step="see" title="Climb to the root, link the roots">

Here are 8 elements, 0 to 7, each in a set of its own. Each set is drawn as a tree, root at the top, with an arrow from
every element to its parent, above the arrays parent[x] and rank[x]. At the start every element is its own parent: all 8
are roots.

<Explore slug="union-find" settings={{ start: 'singletons' }} caption="Union 0 and 1, then 2 and 3, then 0 and 2. The first union finds two roots of rank 0, hangs 1 under 0 (parent[1] = 0) and raises rank[0] to 1. The second hangs 3 under 2 the same way. The third links two roots of rank 1: 2 goes under 0, rank[0] becomes 2, and 3 is now two links below the root." />

The sets live entirely in those links: two elements are connected exactly when their climbs reach the same root, and
union points one root at the other. Neither tree is walked or copied: merging two sets of a million costs two finds and
one link.

The cost to watch is the climb. A find follows one link per level, so it is as slow as the tree is tall. Suppose union
always hung a's root under b's. Then union(0, 1), union(0, 2), union(0, 3) and so on would each hang the whole tree
under one new element, building a chain: 0 under 1 under 2 under 3. With n elements, find(0) climbs n − 1 links: O(n).

**Union by rank** prevents that. Every root keeps a rank, an upper bound on its tree's height, and union hangs the root of
lower rank under the other, so the merged tree keeps the larger rank and its height bound does not grow. Only a tie
raises it: the new root's rank goes up by one (on a tie, this visualiser hangs b's root under a's). Rank 1 needs two
elements and rank 2 needs two rank-1 trees, so at least four: a root of rank r has at least $2^r$ elements in its tree.
So no tree is taller than log₂ n, which is 19 links for a million elements.

**Path compression** flattens the trees further, almost for free. A find climbs the whole path anyway, so once it knows
the root it points every element it passed straight at it, and the next find from any of them takes one hop.

<Explore slug="union-find" settings={{ start: 'tall' }} caption="Find 7, then find 7 again. 7 sits three links below the root, 0, as deep as union by rank allows in a tree of 8. The first find climbs from 7 to 6, 4 and 0, then re-points 7 and 6 straight at 0 (4 already pointed there). The second find takes one hop." />

<KeyIdea>

**Each set is a tree stored in one parent array, and its root names it.** find climbs to the root, connected compares
two roots, and union links one root under the other. Union by rank keeps every tree at most log₂ n tall, and path
compression flattens every path a find climbs, so finds stay short.

</KeyIdea>

</Section>

<Section step="do" title="Union-find in code, and where it pays">

In code, union-find is two lists of numbers. `find_root` (`findRoot` in JavaScript and TypeScript) is recursive, as in
the [recursion lesson](/learn/recursion): a root is the base case, and any other element gets its parent's root, stores
it as its own parent and returns it. Those stores, made as the calls return, are path compression. (The visualiser
makes them in a second loop instead.) `union` finds both roots, stops if they match, and otherwise hangs the lower-ranked root
under the other.

The program starts from two sets: 0 is the root of 0 to 3, with 3 under 2, and 4 is the root of 4 and 5. The list is
`forest` at the top and `parent` inside the functions, two names for one list. Each real merge returns 1, so `groups`
counts the sets left.

On the way, 3 was re-pointed straight at 0, and the program prints 1: one set left."

The link goes between roots, and that matters more than it looks.

>

parent[a] is a's only link to the rest of its set. Overwrite it and a moves to b's tree with everything below it, but its
old root and the other branches stay behind: one set split, not two merged. A root has nothing above it to lose, so
linking two roots carries both whole trees. Union links the roots, never the elements it was given.

</Misconception>

The classic user is **Kruskal's algorithm** for a minimum spanning tree, the cheapest set of edges connecting every node
of a weighted graph. It takes edges cheapest first and keeps one only if its ends are not yet connected; otherwise it
would close a cycle.

<Explore slug="union-find" settings={{ start: 'singletons' }} caption="Play Kruskal's algorithm on nodes 0, 1 and 2: union 0 and 1, then 1 and 2, then ask Connected? for 0 and 2. The second union climbs from 1 to its root, 0, and hangs 2 (rank 0) under 0 (rank 1), so rank[0] stays 1. Both finds then reach 0: an edge between 0 and 2 would close a cycle, so Kruskal's algorithm skips it." />

Counting a graph's **connected components** is the same loop: start with n sets, union the ends of every edge, and
subtract one for each union that links two roots, as `groups` did. Either way, the check must compare roots, not
parents.

      answer: 1,

A parent only says where the climb goes next. Union re-points a single root, so everything below it keeps its old
parent, and compression only flattens paths that finds have walked: after the three unions in the first visualiser, 1
points at 0 but 3 at 2. Only the root names a set, so compare find(a) with find(b).

</Misconception>

How fast is it in the end? With both tricks, any m operations on n elements take O(m α(n)) time in total, where α, the
inverse Ackermann function, is at most 4 for any n you could ever store. That is nearly constant per operation, but
only on average over the sequence, and that caveat matters.

<Misconception
  id="every-find-constant"
  title="With path compression, every find takes constant time"
  probes={[

      q: 'With union by rank and path compression, element 7 is three links below its root, and no find has passed it yet. How many links does find(7) follow?',

      answer: 2,
      trap: 0,
      why: 'Compression flattens a path only after a find has climbed it. This find climbs all 3 links, then points 7 and the element above it at the root, so the next find(7) takes one hop.',
    },
    {
      q: 'With union by rank and path compression, what does O(α(n)) per operation promise?',
      choices: ['Every single operation takes at most about α(n) steps', 'An average over the sequence: one find can still climb up to about log₂ n links', 'Nothing useful, since α(n) grows like log n'],
      answer: 1,
      trap: 0,
      why: 'The bound is amortised: m operations take O(m α(n)) in total. A long climb leaves its path flat for later finds, and α(n) is at most 4 for any realistic n.',
    },
  ]}
>

Compression helps later finds, not the one doing it: a find climbs every link of its path before re-pointing them, and
with union by rank that can still be log₂ n links. The O(α(n)) is **amortised**, an average over the sequence, paid for
by each long climb leaving its path flat. Say "nearly constant, amortised", not "constant".

</Misconception>

Union-find only merges, though: it has no operation that splits a set apart again.

<Section step="recap" title="What to remember">

- Union-find keeps disjoint sets as trees in one parent array. A root is its own parent and names its set.
- find climbs to the root, and connected(a, b) is find(a) = find(b): compare roots, never parents.
- union(a, b) links the two roots. Overwriting a non-root's parent splits its set instead.
- Union by rank keeps every tree at most log₂ n tall; path compression points each path a find climbs at the root.
- Together, m operations take O(m α(n)): nearly constant each, amortised. Sets merge but never split.
- Next: [minimum spanning trees](/learn/minimum-spanning-trees), where [Kruskal's algorithm](/visualisers/kruskals) uses union-find to skip edges that
  would close a cycle. Practise with [Count Connected Groups](/practice/connected-components) and
  [The Extra Edge](/practice/redundant-connection), or open the [union-find visualiser](/visualisers/union-find) to try
  more operations.

</Section>
