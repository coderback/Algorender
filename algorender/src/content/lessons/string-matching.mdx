<Section step="hook" title="Find it without starting over">

You search a long report for a word, and every place it occurs lights up; biologists look for short sequences in a
genome of three billion letters. The job: find every position where a **pattern** of m letters occurs in a **text** of n
letters.

The obvious way lines the pattern up under the text and compares letter by letter until one differs, then moves the
pattern one place right and starts again. On ordinary text a mismatch usually comes at once. But search a million a's
for “aaaab”, and at almost every position four letters match before one fails: about five million comparisons, and
O(n·m) in the worst case, because every fresh start reads again letters already seen.

This lesson shows two ways not to start over. **KMP** (Knuth, Morris and Pratt) uses what it has already read, so it
never moves back in the text. **Rabin–Karp** compares one number per window, a hash, instead of m letters.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="text and pattern">The text T has n letters and the pattern P has m. P occurs at position s when T[s..s + m − 1] equals P. Two occurrences may overlap.</Term>
  <Term name="shift">Where the pattern sits under the text. The naive search tries every shift from 0 to n − m.</Term>
  <Term name="border">A string that is both a proper prefix and a suffix of another, where proper means shorter than the whole. “ab” is a border of “abcab”.</Term>
  <Term name="lps table">lps[i] is the length of the longest border of P[0..i], the pattern's first i + 1 letters: its longest proper prefix that is also a suffix. Also called the failure function.</Term>
  <Term name="rolling hash">A window's hash, updated rather than worked out again as the window slides: the leaving letter's share comes out and the entering letter's goes in.</Term>
</Terms>

</Section>

<Section step="see" title="Slide the pattern, keep what matched">

Take the text “abcabcabd” and the pattern “abcabd”. At shift 0 the naive search matches a, b, c, a and b, then T[5] = 'c'
fails against 'd'. It moves the pattern to shift 1 and compares T[1] with P[0], going back four letters in the text.

It doesn't need to. Those five text letters are known: they are “abcab”, the pattern's own start. A match at shift 1
would need “bcab” to begin the pattern, and one at shift 2 would need “cab” to; neither does. At shift 3 the last two
matched letters, “ab”, are the pattern's first two. So the pattern can slide 3 places with “ab” already lined up, and
compare T[5] with P[2] next.

That depends only on the pattern: “ab” is the longest border of “abcab”. So KMP first works out the longest border of
every prefix of the pattern, the **lps table**. For “abcabd” it is 0, 0, 0, 1, 2, 0; lps[4] = 2 is the “ab”.

<Explore slug="kmp" settings={{ input: 'text: abcabcabd | pattern: abcabd' }} caption="The run builds the table first, with 6 comparisons. The search matches “abcab”, fails at T[5] = 'c' against 'd', slides the pattern 3 places to keep “ab” lined up, and compares T[5] again, with P[2]. It finds the match at 3 with 10 comparisons; the naive search, in the readout, makes 14." />

<KeyIdea>

**When j letters have matched and the next one doesn't, the j text letters just matched are known: they are P[0..j − 1]. The
longest border of that prefix, lps[j − 1], is how many of them can still start a match, so KMP slides the pattern to
keep exactly those and compares the same text letter again. Each comparison moves the text pointer on or slides the
pattern right, and neither ever moves back: at most 2n comparisons. With the table, built the same way in O(m), KMP is
O(n + m).**

</KeyIdea>

The table pays for itself on the naive search's worst case: a run of one letter, and a pattern ending in another.

<Explore slug="kmp" settings={{ input: 'text: aaaaaaaaaaaaaaaaaaaaaaab | pattern: aaaab' }} caption="23 a's and a b, searched for “aaaab”. Each of the naive search's 20 shifts matches four a's before the fifth comparison decides: 100 comparisons. After each mismatch KMP keeps three a's (lps[3] = 3), so it compares each text letter at most twice: 43 comparisons, plus 7 for the table." />

</Section>

<Section step="do" title="Building the table, then hashing windows">

The table is built with the same move, run on the pattern against itself. `border` is the length of the border found
so far, and the next pair to compare is P[i] and P[border]. If they match, lps[i] = border + 1 and i moves on. If not,
fall back to the next-longest border, lps[border − 1], and try again; only when no border is left is lps[i] = 0. Each
comparison moves i on or shrinks the border, and the border, growing at most one per step of i, can't shrink more than
m times: under 2m comparisons, O(m). Here it is for “aabaaab”.

The search falls back the same way, j becoming lps[j − 1] after a mismatch, and that step is easy to get wrong.

<Misconception
  id="skip-matched-letters"
  title="After a mismatch, the pattern can jump past every letter that matched"
  probes={[
    {

      answer: 1,
      trap: 0,
      why: 'T[1..3] is “aab”. The matched “aa” has the border “a”, so a match can start on its last letter. KMP keeps that a (lps[1] = 1) and finds the match at 1.',
    },
    {
      q: 'When is it safe to slide the pattern past all j letters that just matched?',
      choices: ['Always: those letters have already been read', 'Only when P[0..j − 1] has no border, so lps[j − 1] = 0', 'Only when j is 1'],
      answer: 1,
      trap: 0,
      why: 'A border is a stretch at the end of what matched that is also the pattern’s start, so a match could begin there. Only with no border can the pattern skip all j letters.',
    },
  ]}
>

Sliding past everything that matched is only safe when the matched part has no border. If its end repeats the pattern's
start, a match can begin inside it, and jumping past can miss it. KMP slides by j − lps[j − 1], not by j, keeping
exactly the letters that could still start one: in the first run above, the “ab” at the end of “abcab”.

</Misconception>

<Misconception
  id="border-no-overlap"
  title="A border's prefix and suffix can't overlap"
  probes={[
    {
      q: 'What is the longest border of “aaaa”?',
      choices: ['“aa”', '“aaa”', '“aaaa”'],
      answer: 1,
      trap: 0,
      why: '“aaa” is both the first three letters and the last three, sharing two letters, which is allowed. “aaaa” itself is too long: a border must be shorter than the whole.',
    },
    {
      q: 'KMP searches “aaaaa” for “aaa” and reports a match at 0. Where does the next match it reports start?',
      choices: ['1', '2', 'There is no other match'],
      answer: 0,
      trap: 1,
      why: 'lps[2] = 2, since “aa” is a border of “aaa”. After the match the pattern keeps two letters and slides one place, and the next letter completes a match at 1, then another at 2.',
    },
  ]}
>

A border only has to be shorter than the whole string; its two copies may share letters. “abca” is a border of
“abcabca”, and the lps table of “aaaa” is 0, 1, 2, 3. Overlapping borders are how KMP finds overlapping matches: in
the challenge above, after the match at 0, lps[2] = 2 kept two a's, and the pattern slid one place, onto the match at 1.

</Misconception>

Rabin–Karp takes a different shortcut: it compares each window's hash with the pattern's. Equal words always get equal
hashes, so a window with a different hash is skipped unread. The visualiser's hash is like the one in
[the hash tables lesson](/learn/hash-tables), with smaller numbers: letters are digits from a = 1 to z = 26, read in
base 26, keeping the remainder mod 101. For “car” that is (3 × 26² + 1 × 26 + 18) mod 101 = 52.

Hashing each window from scratch would cost m steps. So the hash **rolls**, like a
[sliding window](/learn/sliding-window)'s running total: take out the leaving letter's share (its value × $26^{m-1}$),
multiply the rest by 26, and add the entering letter, a few steps whatever m is.

<Explore slug="rabin-karp" settings={{ input: 'text: racecar | pattern: car' }} caption="Search “racecar” for “car”, which hashes to 52. Windows 0, 2 and 3 (“rac”, “cec” and “eca”, hashes 77, 40 and 25) are skipped without reading a letter. Window 1, “ace”, also hashes to 52: a spurious hit, rejected by one letter comparison, 'a' against 'c'. Window 4 hashes to 52 and its 3 letters agree: a match at 4. That is 5 hash comparisons and 4 letter comparisons." />

<Misconception
  id="equal-hash-is-match"
  title="Equal hashes mean the window matches"
  probes={[

      answer: 1,
      trap: 0,
      why: 'Equal hashes only say the window might match, and the first letter comparison shows it doesn’t: a spurious hit. Skipping without a check is only right when the hashes differ.',
    },
    {
      q: 'A Rabin–Karp search for an 8-letter pattern switches its modulus from 101 to a prime near a billion. What happens to spurious hits?',
      choices: ['They become impossible, so the letter check can go', 'They become rare, but the letter check is still needed', 'They become more common'],
      answer: 1,
      trap: 0,
      why: 'There are about 200 billion 8-letter windows and only a billion values, so some different windows must share one. A big modulus makes a clash unlikely, never impossible.',
    },
  ]}
>

A hash squeezes every window into one of a few values, 101 here. There are 17,576 three-letter words, so about 174 share
each value on average. Different hashes prove two words differ; equal hashes only mean “maybe”, so Rabin–Karp compares
the letters of every hit. A larger modulus makes spurious hits rarer; with more possible windows than values, never
impossible.

</Misconception>

So Rabin–Karp is expected O(n + m), not guaranteed: each hit costs up to m letter comparisons, and a weak hash, or
aaaa…a searched for aaa, makes nearly every window a hit: O(n·m). Its strength is many patterns of one length at once:
keep their hashes in a hash set and look up each window's hash, in one pass.

A third linear method, the [Z-algorithm](/visualisers/z-algorithm), joins the pattern, a separator and the text into one
string and measures, at every position, how far the letters agree with its start; where that reaches m, the pattern
starts. Like KMP it reuses earlier comparisons, so it is O(n + m) too.

</Section>

<Section step="recap" title="What to remember">

- The naive search restarts after every mismatch and reads the text again: O(n·m) on text like aaaa…ab.
- A border is a proper prefix that is also a suffix; its two copies may overlap. lps[i] is the length of the longest
  border of P[0..i], built by extending a border or falling back to a shorter one, in O(m).
- After a mismatch with j letters matched, KMP sets j = lps[j − 1] and compares the same text letter again. The text
  pointer never moves back: O(n + m) in all.
- Rabin–Karp rolls a window's hash in O(1) and compares letters only on a hit. Hits can be spurious, so the check stays:
  expected O(n + m), O(n·m) at worst.

  ([its visualiser](/visualisers/manacher)), and [tries](/learn/tries), for many words at once. Practise with
  [Longest Palindromic Substring](/practice/longest-palindromic-substring) and

  [Rabin–Karp](/visualisers/rabin-karp) and [Z-algorithm](/visualisers/z-algorithm) visualisers.
