<Section step="hook" title="Work out where it is, then look there">

You are signing up to a site with ten million accounts, and as you type a username it tells you at once whether the
name is taken. Checking the names one by one would take up to ten million comparisons. Keeping them sorted and using
[binary search](/learn/binary-search) cuts that to about 24. A **hash table** usually needs one or two, however many
names there are.

It borrows the trick that makes an array fast. An array never searches for index i: it works out where cell i is. A
hash table works out where a *key* belongs, from the key itself, and looks only there.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="hash function">Turns a key into a whole number, its hash. The same key always gives the same number; a good hash gives different keys unrelated-looking numbers.</Term>
  <Term name="bucket">The table is an array of m buckets, numbered 0 to m − 1. A key goes in bucket hash(key) mod m, the remainder when its hash is divided by m.</Term>
  <Term name="collision and chaining">A collision is two different keys landing in the same bucket. With chaining, each bucket keeps a list, its chain, of every key that landed there.</Term>
  <Term name="load factor">Keys per bucket: n keys divided by m buckets. With chaining it is the average chain length, and it can go above 1.</Term>
  <Term name="map and set">A map stores a value with each key, like a Python dict or a JavaScript Map. A set stores keys alone and says whether a key is there.</Term>
</Terms>

</Section>

<Section step="see" title="Work out the bucket, search only there">

This table maps “cat” to 3, “dog” to 7 and “owl” to 5, in 7 buckets. Look up a stored key and a missing one, and count
the keys each lookup compares.

<Explore slug="hash-table" settings={{ start: 'example' }} caption="Get “owl”, then get “emu”. “owl” hashes to 110468, and 110468 mod 7 = 1, so the lookup goes to bucket 1 and finds it with 1 comparison. “emu” lands in bucket 2, which is empty, so the answer is “not found” without comparing a single key." />

Neither lookup touched another bucket. The table's hash function reads the character codes as the digits of a number
in base 31: for “cat”, codes 99, 97 and 116, that is 99 × 31² + 97 × 31 + 116 = 98262. Then **mod 7**, the remainder
after dividing by 7, turns any number into a bucket from 0 to 6: 98262 mod 7 = 3, so “cat” lives in bucket 3. put and
get both work this out the same way, so they always agree.

Different keys can leave the same remainder: seven buckets can't give a million words one each, and even a handful of
keys often clash. So each bucket holds a **chain** of its keys, and a lookup walks it, comparing keys, until it finds
the one it wants or reaches the end.

<Explore slug="hash-table" settings={{ start: 'collisions' }} caption="“cat”, “ant” and “yak” all hash to bucket 3. Get “yak”: the lookup goes straight to bucket 3 and compares “cat”, “ant” and “yak”, 3 comparisons. “dog”, in bucket 6, is never looked at." />

<KeyIdea>

**A hash table computes a key's bucket, hash(key) mod m, so put, get and delete only ever search one bucket's chain.
With a hash function that spreads keys evenly, a chain holds n/m keys on average, the load factor. Keep that below a
fixed limit and each operation is O(1) on average, however many keys the table holds.**

</KeyIdea>

Keeping the load factor down is the table's own job. This one, like Java's HashMap, lets it reach 0.75 and no more.
A put that pushes past that moves the table to more buckets: here the first prime above twice the old count, so 7
buckets become 17 (Java's HashMap doubles instead). A key's bucket depends on m, so every key's bucket is worked out
again: a **rehash**.

<Explore slug="hash-table" settings={{ start: 'nearly-full' }} caption="This table holds 5 keys in 7 buckets, a load factor of 0.71. Put “eel” with any value: it lands in the empty bucket 4, and 6/7 = 0.86 is over 0.75, so the table allocates 17 buckets and rehashes all 6 keys. “cat” moves from bucket 3 to bucket 2, and “gnu” and “eel” end up sharing bucket 0." />

</Section>

<Section step="do" title="A map in code, and where it slows down">

Here is a whole chained map: buckets is a list of 5 chains of `[key, value]` pairs, and the hash is the sum of the key's
character codes. put updates the pair holding its key or appends one, and get walks the same chain for the value. The
program puts “no” and “on”, then gets “on”.

/>

Summing the codes is a weak hash. It ignores letter order, so anagrams always collide, and it bunches short keys
together: every three-letter lowercase word sums to between 291 and 366, so they land in at most 76 buckets however big
the table. The visualiser's hash multiplies by 31 at each character, so position counts, and “cat” and “act” land in
buckets 3 and 5 of 7.

Even the best general-purpose hash can't prevent collisions, and they come sooner than most people expect.

      answer: 1,

>

A good hash scatters keys like random throws, and random throws pile up early. It is the birthday problem: 23 people
are enough for two to share a birthday more often than not, though the year has 365 days, and 23 keys in 365 buckets
collide just as often. A million buckets reach even odds at about 1,200 keys. So a hash table plans for collisions:
every bucket is a chain, and the load factor, not luck, keeps the chains short.

</Misconception>

Short on average is not short always. Bad luck, a poor hash, or an attacker sending keys built to collide can pile many
keys into one bucket (try it on [Break it](/play/break-it)). That is why Python salts its string hash with a random seed
each time it starts, and why Java's HashMap turns a very long chain into a balanced tree.

  id="lookup-always-constant"
  title="A hash table lookup is always O(1)"

      answer: 1,

>

The O(1) is an average, and it rests on two things: a hash that spreads keys evenly, and a load factor kept under a
limit. Take either away and chains grow. If every key lands in one bucket, get compares all n of them one by one: O(n),
no better than a plain list. Expected O(1) and worst-case O(n) are both true of the same table.

</Misconception>

The limit is kept by resizing, and resizing has a trap of its own.

<Misconception
  id="resize-keeps-buckets"
  title="Growing the table leaves keys in their buckets"
  probes={[
    {
      q: '“cat” hashes to 98262 and sits in bucket 3 of a 7-bucket table, since 98262 mod 7 = 3. The table grows to 17 buckets. Which bucket is “cat” in now?',
      choices: ['Bucket 3: growing only adds empty buckets', 'Bucket 2, since 98262 mod 17 = 2', 'Bucket 13: 3 plus the 10 new buckets'],
      answer: 1,
      trap: 0,
      why: 'Its bucket is its hash mod m, and m is now 17. Left in bucket 3, “cat” would never be found: get looks in bucket 2.',
    },
    {
      q: 'Why does a resize visit every key, and not only the keys in crowded buckets?',
      choices: [
        'It doesn’t: keys stay where they are, and only new keys use the extra buckets',
        'Every key’s bucket is its hash mod m, and m has changed, so any key may now belong elsewhere',
        'The keys have to be sorted again',
      ],
      answer: 1,
      trap: 0,
      why: 'get always looks in hash mod the current m, so after m changes a key is found only if it was moved to the bucket that formula now gives.',
    },
  ]}
>

A key's bucket is hash(key) mod m, so it depends on m as much as on the key: in the set above, adding 5 after 24 grows
the table to 17 buckets and spreads the chain 3, 10, 17, 24 over buckets 3, 10, 0 and 7. Keys left in place would be
looked for in the wrong bucket, so a resize rehashes them all: O(n) for that put. Inserting is still **O(1) amortised**,
as with [a growing array's append](/learn/arrays): the table at least doubles, so after moving n keys it takes about n
more puts to need another resize. It is also why hash mod N reshuffles almost every key when a server joins, which
[consistent hashing](/learn/consistent-hashing) avoids.

</Misconception>

One thing a hash table can't do is sorted order: buckets scatter keys with no regard to which is smaller, so it can't
list its keys in order or find the smallest quickly. That is a job for a [binary search tree](/learn/binary-search-trees).

</Section>

<Section step="recap" title="What to remember">

- A key lives in bucket hash(key) mod m, so put, get and delete search one bucket's chain, not every key.
- Collisions come early, long before the table is full. Chaining keeps each bucket's keys in a list.
- The load factor n/m is the average chain length. Kept below a limit, with an even hash, every operation is O(1) on
  average; if everything collides, it is O(n).
- Passing the limit grows the table by a constant factor and rehashes every key, because buckets depend on m: O(n) for
  that put, O(1) amortised.
- A set is the same table without values. Neither keeps its keys in sorted order.
- Next: **Bloom filters**, which hash each item to a few bits ([the Bloom filter visualiser](/visualisers/bloom-filter)),
  and **string matching**, where [Rabin–Karp](/visualisers/rabin-karp) hashes a sliding window of text. Hash maps also
  sit inside [caches](/learn/caching), and [consistent hashing](/learn/consistent-hashing) replaces mod N across
  servers. Practise with [Two Sum](/practice/two-sum),
  [Spot a Repeated Number](/practice/contains-duplicate) and [Group Anagrams](/practice/group-anagrams), or open the
  [hash table](/visualisers/hash-table) and [hash set](/visualisers/hash-set) visualisers to try more operations.

</Section>
