<Section step="hook" title="Add one cache server, lose most of your cache">

A site keeps hot data in a cache spread over three servers. The simplest way to pick a server for a key is
`hash(key) mod 3`: quick, even, and every client gets the same answer without asking anyone.

Then traffic grows and a fourth server joins. Now it's `hash(key) mod 4`, and a key stays on the same server only if
its hash leaves the same remainder for 3 and 4. That's about 1 key in 4. The other three quarters suddenly look up the
wrong server, miss, and all hit the database at once, just when the site was already busy.

Consistent hashing fixes this: when a server joins or leaves, only about $1/N$ of the keys move, and everything else
keeps its home.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="the ring">Every possible hash value, from 0 to $2^{32} - 1$, bent round into a circle: 0 at the top, values growing clockwise, and the largest one sitting just before 0 again.</Term>
  <Term name="server node">A server placed on the ring at the hash of its name. Its colour marks it and the arc it owns.</Term>
  <Term name="the owner rule">A key belongs to the first server node clockwise from where the key hashes, wrapping round past the top.</Term>
  <Term name="virtual nodes">Several places on the ring for each server (A#0, A#1, …), so each server owns many small arcs instead of one big one.</Term>
</Terms>

</Section>

<Section step="see" title="Keys find their server by walking clockwise">

Twelve fruit names are stored on three servers, each with a single node. Look up a key, then add server D and watch
which keys change colour.

<Explore slug="consistent-hashing" settings={{ start: 'vnodes-1' }} caption="One node per server: each server owns the arc that ends at its node." />

Notice the load readout too. With one node each, the arcs are whatever lengths the hash happens to give: here C owns
60% of the ring and stores 9 of the 12 keys.

<KeyIdea>

**A key's owner changes only when a node appears or disappears between the key and its old owner.** A joining node
takes the arc just before it; a leaving node hands its arc to the next node clockwise. Every other key keeps its server,
so a change moves about $1/N$ of the keys, where `mod N` moves most of them.

</KeyIdea>

</Section>

With one node per server, the arcs are as uneven as the hash makes them: in the first example C owns 60% of the ring
and 9 of the 12 keys. **Virtual nodes** fix it: each server gets many places on the ring, so its share is the sum of

different neighbours instead of dumping everything on one.

<Section step="recap" title="What to remember">

- Hash keys and servers onto **one ring**; a key belongs to the **first server node clockwise**, wrapping round.
- A server joining or leaving only changes the arcs beside its nodes, so about **$1/N$ of the keys move**. With `hash mod N`, most of them do.
- One node per server gives **lopsided arcs**; **virtual nodes** even out the load and spread a leaving server's keys.
- To keep copies, walk on past the owner to the **next distinct servers**. Memcached clients, Cassandra, Riak and CDNs all work this way.

</Section>
