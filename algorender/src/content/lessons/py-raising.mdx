<Section step="hook" title="Saying no">

`int("ten")` doesn't guess or hand back `None`: it stops with a `ValueError` that says what was wrong. Your own
functions can do the same. A `withdraw` that quietly returns `-30` for 50 out of 20 passes a wrong answer on, to
cause trouble far away. Better to refuse, right there, and say why.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="raise">A statement that starts an error on purpose: `raise ValueError("amount can't be negative")`.</Term>
  <Term name="re-raise">Sending a caught error on up with a bare `raise`, after doing something with it.</Term>
  <Term name="assert">A check that your own code did what you meant: `assert total >= 0` raises `AssertionError` if not.</Term>
</Terms>

```python
def withdraw(balance, amount):
    if amount > balance:
        raise ValueError(f"can't take {amount}, only {balance} left")
    return balance - amount
```

`raise` stops the function on that line: not even the `return` runs. The error lands on the calling line. If that
line is in a `try` with a matching `except`, the `except` runs; if not, the error leaves that function too, and so
on up. If nothing catches it, `withdraw(20, 50)` stops the program with a traceback ending
`ValueError: can't take 50, only 20 left`.

**Pick the type that fits.** `ValueError` is for a value of the right kind that won't do, like a negative amount.
`TypeError` is for the wrong kind, like a string where a number belongs. Put the value in the message.

**Re-raising.** To note an error but let the caller decide, end the `except` with a bare `raise`, which sends it
on up:

```python
try:
    balance = withdraw(balance, amount)
except ValueError as e:
    print("refused a withdrawal:", e)
    raise
```

**An error of your own.** This makes a new kind of error, named `NotEnoughStock`:

```python
class NotEnoughStock(Exception):
    pass
```

Classes come in unit 7, so take it as a recipe: `(Exception)` makes the new name a kind of error, and `pass` adds
nothing more. Now `raise NotEnoughStock("only 3 left")` and `except NotEnoughStock as e:` work like the built-in
ones, and a caller can catch exactly this error and no other.

**assert or raise?** `assert` is for your own mistakes. Bad input from a caller isn't one, so refuse it with
`raise`. Asserts can also be switched off, and then they check nothing.

</Section>

<KeyIdea>

**`raise` stops the function there and sends the error up through its callers, skipping the rest of each, until
a matching `except` catches it.** Raise one when a function gets input it can't use, rather than returning a wrong
answer or `None`.

<Section step="recap" title="What to remember">

- `raise ValueError("what was wrong")` refuses bad input instead of returning a wrong answer.
- `raise` stops the function; the error travels up through the callers until an `except` catches it.
- `ValueError` for a bad value, `TypeError` for the wrong kind, with the value in the message.
- A bare `raise` in an `except` sends the same error on up.
- `class NotEnoughStock(Exception): pass` makes an error of your own.
- `assert` checks your own mistakes; `raise` refuses a caller's.

</Section>
