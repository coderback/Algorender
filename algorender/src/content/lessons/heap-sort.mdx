<Section step="hook" title="A guarantee with nothing to spare">

[Quick sort](/learn/quick-sort) sorts a million random values in about 25 million comparisons, but the wrong order costs
it 500 billion. [Merge sort](/learn/merge-sort) never needs more than about 20 million, but it borrows a second array as
long as the first. The Linux kernel wants neither: its code runs on a small, fixed stack, where deep recursion and big
buffers are unwelcome, and a sort that some input makes crawl is a weakness. So the kernel's array sort is
**heap sort**: O(n log n) on every input, with a few variables as its only extra memory.

The idea comes from the [heaps lesson](/learn/heaps): a max-heap keeps its largest value on top, so taking the top out
again and again hands the values back largest first. The trick is where they go: each removal frees the last cell of the
heap, and that cell is exactly where the value removed belongs.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="max-heap">A complete binary tree in the array, with the children of index i at 2i + 1 and 2i + 2 and no child larger than its parent, so the largest value is at index 0.</Term>
  <Term name="build-heap">Sifting down every parent, from the last, at ⌊n/2⌋ − 1, back to the root, which makes the whole array a max-heap in O(n).</Term>
  <Term name="sift down">Swapping a value with its larger child while that child is larger, so it sinks until the heap holds again.</Term>
  <Term name="heap part and sorted part">Positions 0 to size − 1 form the heap; positions size to n − 1 hold the largest values in their final places.</Term>
  <Term name="stable">Equal values keep their starting order, which matters when you sort records by one field.</Term>
</Terms>

</Section>

Then each pass swaps the root into the last cell of the heap and sifts the new root down: 77 lands in position 7, then 64 in position 6, and the sorted part grows from the right. 27 comparisons and 21 swaps." />

The first loop is the bottom-up build from the heaps lesson: most values sit near the bottom and barely move, so it
costs O(n).

The second loop does the sorting. The root is the largest value in the heap, so swap it with the heap's last value: it
now sits where it belongs, since nothing left in the heap is larger. Shrink the heap by one, so that cell is never
touched again. The value that came up to the root was a leaf, usually small, so it sinks back down, swapping with its
larger child.

A heap of n values is about log₂ n levels deep, and a sift-down makes at most two comparisons per level: one to find the
larger child, one to compare it with the sinking value. So the n − 1 passes cost O(n log n), whatever the order of the
input.

<KeyIdea>

**Build a max-heap in the array in O(n). Then, n − 1 times, swap the root, the largest value left, into the last cell
of the heap, shrink the heap by one and sift the new root down in O(log n). The sorted part grows from the right, and
the sort is O(n log n) on every input, with O(1) extra memory.**

</KeyIdea>

Sift-down is a loop, not a recursion, and every move is a swap inside the array, so there is no call stack to grow and
no buffer. Quick sort can't promise the time, and even a careful one keeps O(log n) calls on its stack; merge sort needs
the buffer. Here are heap sort and quick sort on sorted lists, quick sort's worst order:

The whole sort puts the build in front: a sift-down over the whole array, size n, for each parent from ⌊n/2⌋ − 1 down
to 0. Notice which heap it builds to sort smallest first.

Values leave the heap from the top but land in the array from the right. Each pass frees the last cell of the heap,
which in ascending order belongs to the largest value not yet placed, so the heap must hand over its largest: a
max-heap. Python's heapq gets values smallest first from a min-heap (heapify, then heappop n times), but they need a
second list, since the heap still fills the front: O(n) extra memory.

</Misconception>

Does a sorted input help, as it helps insertion sort? Here are the 12 sorted values that cost quick sort 66 comparisons
in its lesson.

47 to 55 comparisons in three orders, where quick sort's ranged from 35 to 66. The order mostly changes the cheap build:
each pass of the second loop brings up a value from the bottom of the heap, usually small, which sinks most of the way
back whatever the order.

The long swaps cost something else. In the Predict run, the 81 that started at position 1 was the first root swapped to
the end and finished last, behind the 81 from position 3.

>

Heap sort moves values in long jumps. The root's swap to the end of the heap carries it past every value in between,
equal ones included, without comparing them, and nothing records which of two equal values came first, so their order
can flip: heap sort is **not stable**. For plain numbers that's harmless. For records sorted by one field, use a stable
sort such as merge sort or Timsort, or sort (key, original position) pairs, at O(n) extra memory.

</Misconception>

On the random order heap sort made 53 comparisons, and quick sort 35 on the same values. A better worst case doesn't
make a faster sort.

  id="guarantee-means-faster"
  title="A better worst case makes heap sort faster than quick sort"
  probes={[
    {

    {
      q: 'A sift-down in a heap of a million values reads index 1,000, then 2,001, then 4,003. Why is that slow on real hardware?',

      answer: 1,
      trap: 0,
      why: 'A processor fetches memory in small blocks and keeps recent ones in its cache. Neighbouring cells arrive together, but a jump from i to 2i + 1 lands in a new block almost every time.',
    },
  ]}
>

On random input heap sort makes more comparisons than quick sort, two per level of every sift-down, and it reads memory
in jumps, from i to 2i + 1. A processor keeps recently used blocks of memory in a small, fast **cache**: quick sort's
partition scans neighbouring cells and finds them there, while heap sort's jumps through a big heap mostly miss. So
libraries use **introsort**: quick sort, switching any part whose recursion goes deeper than about 2 log₂ n levels to
heap sort, as std::sort in the common C++ libraries and Array.Sort in .NET do. Heap sort alone is for when the guarantee
and the O(1) memory matter more than speed, as in the kernel.

</Misconception>

<Section step="recap" title="What to remember">

- Heap sort builds a max-heap in the array bottom-up, in O(n), then n − 1 times swaps the root into the last cell of the
  heap, shrinks the heap by one and sifts the new root down.
- The sorted part grows from the right; the part on the left is a heap, never a sorted list.
- Each sift-down walks at most about log₂ n levels, so heap sort is O(n log n) on every input, with O(1) extra memory
  and no recursion.
- To sort smallest first in place, build a max-heap: each pass fills the last cell of the heap, where the largest value
  left belongs.
- It is not stable, and more comparisons and scattered memory reads make it slower than quick sort, so introsort keeps it
  as a fallback.
