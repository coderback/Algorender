<Section step="hook" title="Two threads, one counter">

A web server counts page views with one line, `count++`, run by whichever thread handles the request. After a busy day
the counter reads 9,970, yet the log shows 10,000 requests. No request failed and no line of code is wrong on its own.

Thirty updates vanished because two threads ran `count++` **at the same time**, and the order their steps happened to
interleave decided the result. That is a **race condition**. The cure is a lock, and locks bring a failure of their
own: threads that wait for each other forever, a **deadlock**.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="thread">An independent line of execution. Threads of one program share its memory, and the scheduler can pause any of them between any two instructions.</Term>
  <Term name="interleaving">One order in which the threads' instructions actually run. The scheduler picks it, so it can change from run to run.</Term>
  <Term name="race condition">The result depends on the interleaving, and some interleavings give a result that running the threads one at a time never would.</Term>
  <Term name="lock (mutex)">Only one thread can hold it. Code between `lock` and `unlock`, the **critical section**, never runs in two threads at once.</Term>
  <Term name="atomic instruction">An instruction the hardware does as one step that nothing can split, such as fetch-and-add or compare-and-swap.</Term>
  <Term name="deadlock">A set of threads each waiting for a lock that another of them holds, so none can ever move.</Term>
</Terms>

</Section>

<Section step="see" title="A lost update">

`count++` looks like one step, but the machine does it in three: **load** `count` into a private register, **add** 1 to
the register, **store** the register back. Here threads A and B each run `count++` once, starting from `count = 0`, and
the scheduler runs them in the order A B A A B B.

<Explore slug="race-conditions" settings={{ preset: 'lost-update' }} caption="Both threads load 0 before either stores, so both store 1 and one increment is lost. The last step tries all 20 interleavings: 18 of them end with count = 1." />

<KeyIdea>

**A thread can be paused between its load and its store. If another thread updates the variable in that gap, the first
thread's store writes back a stale value and the other update is lost.** Each instruction is correct; the trouble is
what can happen between them.

</KeyIdea>

    },

>

In source code it is one line, but the machine loads the value, adds 1 and stores it back as separate steps, and a
thread can be paused between any two of them. If another thread changes the variable in between, the store overwrites
that change. Two unlocked `count++` can end at 1 instead of 2.

</Misconception>

Most of the interleavings go wrong here, so why do real programs usually seem to work? Because the threads rarely hit
those three steps at the same moment: a scheduler lets a thread run thousands of instructions before switching, and on
separate cores the two updates must overlap within a few nanoseconds.
With three threads there are 1,680 interleavings: 1,404 end at 1, 270 at 2, and only the 6 that run one thread at a
time reach 3.

<Section step="do" title="Fixing races, and the price of locks">

Wrap `count++` in a lock and only the thread holding the lock can run the three steps. A thread that reaches `lock m`
while another holds it has to wait.

<Explore slug="race-conditions" settings={{ preset: 'mutex' }} caption="B reaches the lock while A holds it, so it waits. Every interleaving now ends at 2." />

For a single number there is a cheaper fix: an **atomic** instruction such as fetch-and-add does the load, the add and
the store as one step that nothing can split, so no lock is needed. **Compare-and-swap** is the general version: store
the new value only if memory still holds the value you read, and otherwise read again and retry.

<Explore slug="race-conditions" settings={{ preset: 'atomic' }} caption="One fetch-and-add per thread: count always ends at 2." />

The withdrawals went wrong even though the subtraction was atomic.

<Misconception
  id="atomic-steps-are-enough"
  title="If every step is atomic, the code is safe"
  probes={[
    {
      q: 'The balance is 100. Two threads each check balance ≥ 80, then subtract 80 with an atomic instruction. With no lock, what can the balance end at?',
      choices: ['Only 20', '20 or −60', 'Only −60', '20 or 100'],
      answer: 1,
      trap: 0,
      why: 'If both checks run before either subtraction, both see 100 and both subtract: −60. Run one after the other, the second check fails: 20.',
    },
    {
      q: 'Which change makes those two withdrawals safe?',
      choices: ['Make the subtraction atomic', 'Hold one lock around both the check and the subtraction', 'Check the balance twice', 'Run the withdrawals on a faster CPU'],
      answer: 1,
      trap: 0,
      why: 'The subtraction is already atomic. What must not be split is the check together with the act, so both go inside one critical section.',
    },
  ]}
>

Atomic steps stop a single update from being torn apart, but they don't stop another thread from running **between**
two of your steps. In **check-then-act** code (check the balance, then withdraw) the check can be stale by the time
you act. The check and the act have to be one critical section, under one lock.

</Misconception>

<Explore slug="race-conditions" settings={{ preset: 'locked-withdraw' }} input caption="The check and the subtraction inside one lock: B waits, then sees 20 and stops. Try your own schedule, e.g. withdraw x2; schedule: A B A B A B." />

Locks have a cost. A waiting thread does no useful work, and a lock held across slow code makes the threads take turns,
so adding threads stops helping. Programs therefore use several smaller locks, and that opens the door to a new
failure. P1 takes R1 then R2; P2 takes R2 then R1.

<Explore slug="deadlock" settings={{ preset: 'opposite' }} caption="P1 holds R1 and waits for R2; P2 holds R2 and waits for R1. The waits form a cycle, so neither can ever move." />

<KeyIdea>

**A deadlock is a cycle of waits: each thread holds a lock the next one needs.** With one holder per lock it needs all
four of Coffman's conditions: mutual exclusion, hold and wait, no preemption, and circular wait. Break any one and
deadlock is impossible. The usual fix breaks circular wait: **take locks in one global order**.

</KeyIdea>

With both processes taking R1 before R2, P2 may wait, but it waits for a lock whose holder needs nothing P2 holds, so
the circle can't close.

<Explore slug="deadlock" settings={{ preset: 'same-order' }} caption="Same schedule, one lock order: P2 waits for R1, but no cycle ever forms and both finish." />

Every thread in a deadlock can be correct on its own. The deadlock lives in the combination: the order in which they
take shared locks, and the timing that lets each grab its first lock before the others' second. You fix it across the
threads, by agreeing one lock order (or taking all the locks at once), not by hunting for the faulty thread.

</Misconception>

Dijkstra's **dining philosophers** is the classic case: five philosophers round a table with a fork between each pair.
Each picks up the fork on one side, then the other. If all five lift their first fork together, the waits close a
circle.

<Section step="recap" title="What to remember">

- `count++` is load, add, store. Threads can be paused between steps, so unlocked updates get lost, and only some interleavings show it, which is why tests miss races.
- A lock makes a critical section run in one thread at a time; atomic instructions (fetch-and-add, compare-and-swap) make a single update indivisible.
- Check-then-act needs the check and the act in one critical section: atomic steps alone aren't enough.
- Locks make threads wait. A cycle of waits is a deadlock; it needs all four Coffman conditions, and one global lock order rules it out.

</Section>
