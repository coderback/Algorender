<Section step="hook" title="Twenty guesses for a million names">

Think of a number between 1 and 1,000,000 and let a friend guess. If you only say "yes" or "no", they could need a
million guesses. If you say "higher" or "lower", they need at most **20**, because every answer throws away half of
what is left: a million, half a million, a quarter million… down to one in about 20 halvings.

Binary search is that game played on a sorted array. It is how a dictionary lookup, a database index or `git bisect`
finds things fast. The catch is the word *sorted*: the "higher or lower" answer only means something when the order is
fixed.

The number of halvings it takes to shrink $n$ items to one is $\log_2 n$, so binary search needs at most
$\lceil \log_2 (n+1) \rceil$ probes, against up to $n$ for checking every element.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="lo and hi">The ends of the **window**: the positions that could still hold the target. Everything outside has been ruled out.</Term>
  <Term name="mid">The middle of the window, ⌊(lo + hi) / 2⌋. The only element the algorithm actually looks at each step.</Term>
  <Term name="probe">One comparison of A[mid] with the target. Counting probes is how we measure the work.</Term>
  <Term name="sorted order">The promise that makes the trick legal: everything left of mid is no bigger, everything right is no smaller.</Term>
</Terms>

</Section>

<KeyIdea>

**If the target is in the array, it is always inside the window [lo, hi].** Each step keeps that true while making the
window at least one element smaller, so the search must end: either at the target, or with an empty window that proves
the target is not there.

</KeyIdea>

</Section>

<Misconception
  id="keep-mid"
  title="hi ← mid instead of hi ← mid − 1"
  probes={[
    {
      q: 'A[mid] = 40 and the target is 25. Which update is right?',
      choices: ['hi ← mid − 1', 'hi ← mid', 'lo ← mid + 1', 'lo ← mid'],
      answer: 0,
      trap: 1,
      why: '40 > 25 rules out mid itself as well as everything to its right, so the window ends just before mid. Keeping mid can stall the loop once lo = hi.',
    },
    {
      q: 'lo = 3, hi = 3, A[3] = 50 and the target is 20. The code sets hi ← mid. What happens next?',
      choices: ['It returns position 3', 'hi becomes 2 and the search ends', 'The same probe repeats forever', 'It probes A[2] next'],
      answer: 2,
      trap: 1,
      why: 'mid = 3, so hi ← mid leaves hi = 3: lo = hi = 3 again and nothing changes. Removing mid (hi ← mid − 1) is what guarantees progress.',
    },
  ]}
>

If A[mid] is bigger than the target, mid itself is ruled out too. Setting `hi ← mid` keeps it in the window, and when
lo = hi the window never shrinks: the loop runs forever. The rule is that every branch must remove mid.

</Misconception>

<Misconception
  id="unsorted-ok"
  title="Binary search works on any array"
  probes={[
    {
      q: 'A = [9, 2, 7, 4, 8] (not sorted) and the target is 9. The first probe sees A[2] = 7. What happens?',
      choices: ['It searches the right half and reports 9 missing', 'It finds 9 at position 0', 'It sorts the array first', 'It searches both halves'],
      answer: 0,
      trap: 1,
      why: '7 < 9 sends the search right, but 9 sits on the left. On unsorted data one comparison says nothing about the other elements, so binary search can miss a target that is there.',
    },
    {
      q: 'You need to find one value, once, in an unsorted list of n items. What is the fastest correct way?',
      choices: ['Sort it, then binary search: O(log n) in all', 'Binary search it: O(log n)', 'Binary search from both ends', 'Scan it: O(n)'],
      answer: 3,
      trap: 1,
      why: 'Binary search needs sorted data, and sorting costs O(n log n), more than one O(n) scan. Sorting first only pays off when you search many times.',
    },
  ]}
>

On an unsorted array, "A[mid] is too small" says nothing about the elements to the right, so throwing away the left half
can throw away the target. If the data isn't sorted, either sort it first (O(n log n)) or search it linearly (O(n)).

</Misconception>

<Section step="recap" title="What to remember">

- Binary search keeps a **window** that must contain the target if it exists, and halves it with each probe.
- It needs about $\log_2 n$ probes: 20 for a million items.
- Every branch must remove mid, or the window can stop shrinking.
- It only works on **sorted** data. The same idea powers searching over answers too: whenever "too small / too big" is
  monotonic, you can binary search it.

</Section>
