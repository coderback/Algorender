<Section step="hook" title="Do you really need to check every pair?">

Given a list of prices and a gift card, is there a pair of items that spends it exactly? The obvious answer tries every
pair: with $n$ items that is $\tfrac{n(n-1)}{2}$ pairs, about 5,000 for 100 items and 50 million for 10,000.

If the prices are **sorted**, you can do it in at most $n - 1$ checks. The trick is to stop thinking about pairs and
start thinking about **ruling values out**.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="L and R">Two indices: L starts at the smallest value, R at the largest. They only ever move inward.</Term>
  <Term name="sum">A[L] + A[R], compared with the target at every step.</Term>
  <Term name="ruled out">A value that cannot be part of any answer, given what we know. Each step rules out exactly one.</Term>
  <Term name="still possible">The positions between L and R: any answer must lie entirely inside them.</Term>
</Terms>

</Section>

<Section step="see" title="Watch values get ruled out">

<Explore slug="two-pointers" settings={{ preset: 'present', n: 10, seed: 7 }} caption="Each step compares one pair and rules out the smaller or the larger value, with the reason in the narration." />

The reasoning is the whole algorithm:

- If A[L] + A[R] is **too small**, then A[L] plus *anything* still possible is too small, because A[R] is the largest
  thing left. So A[L] can't be in any answer: move L right.
- If the sum is **too big**, A[R] plus anything still possible is too big, because A[L] is the smallest thing left. So
  A[R] is out: move R left.

<KeyIdea>

**Any pair that hits the target lies entirely inside [L, R].** Each step keeps that true and shrinks the range by one, so
after at most $n - 1$ steps you have either found the pair or proved there isn't one. That is O(n) instead of O(n²).

</KeyIdea>

</Section>

<Misconception title="It works on unsorted data too">

The argument "A[R] is the largest thing left" is only true if the array is sorted. On unsorted data, moving L right can
skip the very value you needed. Sort first (O(n log n), still far better than O(n²)), or use a hash set of values you
have seen, which finds a pair in O(n) without sorting.

</Misconception>

<Section step="recap" title="What to remember">

- Two pointers use **order** to rule out one value per step, turning O(n²) pair checks into O(n).
- The invariant: any answer lies inside [L, R].
- The same shape solves 3Sum (fix one value, two-pointer the rest), container with most water, and removing duplicates in place.
- Next: the **sliding window** keeps two pointers moving in the same direction instead of toward each other.

</Section>
