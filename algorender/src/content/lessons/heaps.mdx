<Section step="hook" title="The most urgent first">

An emergency department doesn't see patients in the order they arrive. Each one is given an urgency, whoever is most
urgent goes next, and new patients keep coming through the door. A queue, from [stacks and queues](/learn/stacks-queues),
would hand back whoever has waited longest. This needs a different rule: the item with the **highest priority** comes out
first.

Keep the waiting list sorted and the most urgent is always at one end, but every arrival has to be slotted into place,
shifting up to n entries, as in [arrays](/learn/arrays). Keep it unsorted and arrivals are cheap, but finding the most
urgent means checking all n. A **heap** sits in between. It keeps the list only partly in order, just enough that the
top item is always first. It is a tree laid out in a plain array with no pointers, and a million entries make a tree
just 20 levels deep, so adding or removing one takes at most 19 swaps.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="priority queue">The interface: insert an item, peek at the top one, remove the top one. The top is the smallest key or the largest, depending on the queue. A heap is the usual way to build one.</Term>
  <Term name="complete binary tree">Every level is full except perhaps the last, which fills from the left. Numbered level by level, its nodes leave no gaps, so they pack into an array.</Term>
  <Term name="heap property">In a **min-heap** every parent is no larger than its children, so the smallest value is at the root. A **max-heap** flips the rule, and the largest is on top. Either way, no child beats its parent.</Term>
  <Term name="index arithmetic">Counting from 0, the children of index i are at 2i + 1 and 2i + 2, and its parent is at ⌊(i − 1) / 2⌋: i − 1 halved and rounded down.</Term>
  <Term name="sift up and sift down">How a heap repairs itself after a change: a value swaps with its parent while it beats it (up), or with its better child while that child beats it (down).</Term>
</Terms>

</Section>

<Section step="see" title="A tree with no pointers">

This min-heap holds seven values. Read it as a tree, with 2 at the root, or as the strip under it: the array that
actually stores the values, with each index below its cell. Each node shows its index too. Insert a value and watch both
views change.

<Explore slug="heap" settings={{ start: 'min', seed: 7 }} caption="Insert 5. It joins at the end of the array, index 7. Its parent, at index ⌊(7 − 1) / 2⌋ = 3, holds 70, so they swap; then 5 swaps with 7 at index 1 and stops under the root, 2, which is smaller. Two swaps in a tree four levels deep." />

Nothing stores where a child is. The tree is complete, so numbering its nodes level by level, left to right, gives exactly
the array order, and the children of index i are always at 2i + 1 and 2i + 2. (Some books count from 1, which makes them
2i and 2i + 1 and the parent ⌊i / 2⌋; here, as in Python's heapq, counting starts at 0.)

Notice what the array is not: sorted. It starts as 2, 7, 41, 70, 52, 97, 47, so 70 comes before 52, and 97 before 47.
The heap property only compares each parent with its own children. That is enough for a priority queue, because along
any path up the tree the values never grow, so the smallest of all sits at the root, index 0, and peeking at it is O(1).

Insert keeps the tree complete first: the new value goes into the next free cell, the end of the array. That may break the
heap property with its parent, so it **sifts up**, swapping with its parent while it is smaller. Each swap climbs one
level. Removing the top is the mirror image. Only the last cell can go without leaving a gap, so the last value fills the
hole at the root, and then it **sifts down**.

<Explore slug="heap" settings={{ start: 'min', seed: 7 }} caption="Extract the root. 2 comes out, and the last value, 47, moves from index 6 to the root. It swaps with 7, the smaller of its two children, then stops at index 1, where its children 70 and 52 are both larger." />

At each level the sinking value looks at both children and swaps with the **smaller** one. That child moves up and becomes
the parent of its old sibling, so it has to be no larger than the sibling too. The value stops as soon as it is no larger
than either child, or when it reaches a leaf.

Completeness is what keeps every path short. A tree allowed to grow lopsided could become a chain of n nodes, and sifting
along it would cost O(n). A complete tree has no such chains: each level doubles the room.

<KeyIdea>

**A heap is a complete tree in an array with one rule: no child beats its parent.** Insert appends and sifts up;
removing the top moves the last value to the root and sifts it down. Each walks one path between the root and a leaf, and
a complete tree of n values is only ⌊log₂ n⌋ + 1 levels deep, so both are O(log n). Peek reads index 0 in O(1).

</KeyIdea>

</Section>

<Section step="do" title="Sift up in code, and a faster build">

A priority queue is what you ask for; a binary heap is how it is usually built. Python's heapq module and Java's
PriorityQueue are both binary min-heaps kept in an array. To order tasks by priority in Python, push tuples such as
(priority, task), which compare by their first item first. Dijkstra's algorithm keeps its frontier this way, keyed by
distance (see the [Dijkstra lesson](/learn/dijkstra)), and so do schedulers, event simulations and "top k" problems.

Here is push for a min-heap kept in a plain list. It appends the value, then climbs: work out the parent's index, stop if
the parent is no larger, otherwise swap the two and move up.

A heap is only partly ordered. The heap property compares each parent with its own children and says nothing about
siblings, cousins or anything else, so [1, 4, 2, 9, 5, 3] is a valid min-heap even though 4 comes before 2. That is why a
heap is cheap to keep: insert and remove repair one path, never the whole array. It is also why a heap can't binary
search. To find out whether some value is in it, you may have to look at every node, which is O(n). To get every value
out in order, remove the top n times; that is **heap sort**, and it costs O(n log n).

</Misconception>

Sift down is the step that is easiest to get wrong. A value with two children has a choice to make, one that sift up
never faces, since a node has only one parent.

>

Sift down must swap with the **better** child: the smaller one in a min-heap, the larger one in a max-heap. The child
that moves up becomes the parent of its old sibling, so it has to beat that sibling as well as the sinking value, and only
the better of the two does. Swap with the other one and the heap property breaks at the very spot you were fixing.

</Misconception>

Sometimes all the values arrive at once. Inserting them one at a time costs O(log n) each, O(n log n) in all. Building
**bottom-up** does better. Lay the values out as they are: that is already a complete tree. Every leaf, the second half of
the array, is a heap of one. Then walk backwards from the last parent, index ⌊n/2⌋ − 1, to the root, sifting each value
down. Both subtrees below it are heaps already, so one sift-down makes its whole subtree a heap.

<Explore slug="heap" settings={{ start: 'min-empty' }} caption="Type 9, 8, 7, 6, 5, 4, 3 into Build heap. It starts at index 2, the last parent, and sinks 7, then 8, then 9, which falls two levels: four swaps in all, and 3 ends on top. Inserting the same values one at a time would take 10 swaps, because each new value is the smallest so far and climbs to the root." />

Four swaps against ten is no accident. Counted the obvious way, though, the build looks no better than inserting: one
sift-down per parent, each up to log₂ n levels long.

      q: 'Why is building bottom-up faster than inserting the n values one at a time?',

      answer: 1,
      trap: 0,
      why: 'Inserting sifts each value up, and the many values near the bottom can have a long way to climb: O(n log n) in the worst case. Bottom-up sifts each value down, and the many values near the bottom have almost nowhere to go: O(n).',

>

"n sift-downs of O(log n) each" is a true upper bound, but not a tight one. Only the root can sink the whole height.
Half the nodes are leaves and never move, a quarter sit one level up and sink at most one level, an eighth sink at most
two, and so on: n/4 × 1 + n/8 × 2 + n/16 × 3 + … adds up to fewer than n swaps, so building bottom-up is **O(n)**.
Inserting one value at a time really is O(n log n) in the worst case, as with the descending list above, because there
the many nodes at the bottom are the ones with the long climb.

</Misconception>

<Section step="recap" title="What to remember">

- A binary heap is a complete binary tree stored in an array counted from 0: the children of i are at 2i + 1 and 2i + 2,
  its parent at ⌊(i − 1) / 2⌋. No pointers are stored.
- The heap property only compares parents with their children. The top value is at index 0, so peek is O(1), but the
  array is not sorted, and finding any other value is O(n).
- Insert appends and sifts up; removing the top moves the last value to the root and sifts it down, swapping with the
  better child. Both walk one path in a tree about log₂ n levels deep: O(log n).
- Building a heap bottom-up from n values is O(n), because most nodes sit near the bottom and barely move.
- A priority queue is the interface (insert, peek, remove the top); a binary heap is the usual implementation.
- Next: **heap sort**, which builds a max-heap in place and keeps moving the top to the end of the array
  ([the heap sort visualiser](/visualisers/heap-sort)), and heaps at work in [Dijkstra's algorithm](/learn/dijkstra),
  in [Prim's algorithm](/visualisers/prims) for [minimum spanning trees](/learn/minimum-spanning-trees) and in [meeting rooms](/visualisers/meeting-rooms)
  for **intervals**. Practise with [Smash the Heaviest Stones](/practice/last-stone-weight),
  [Kth Largest in a Stream](/practice/kth-largest-in-stream) and [Kth Largest Number in a List](/practice/kth-largest-element),
  or open the [heap visualiser](/visualisers/heap) to try more operations.

</Section>
