<Section step="hook" title="The same question, asked hundreds of times">

The Fibonacci numbers are defined by themselves: $F(n) = F(n-1) + F(n-2)$, starting from $F(0) = 0$ and $F(1) = 1$.
Code that follows the definition word for word is correct, short, and astonishingly slow: computing $F(40)$ makes over
300 million calls.

It isn't slow because addition is slow. It is slow because it asks the **same questions again and again**. Memoization
fixes that with one idea: write each answer down the first time, and look it up after that. It is the first step
towards dynamic programming.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="call">One run of fib(k). Each call that isn't a base case makes two more calls.</Term>
  <Term name="call stack">The calls still waiting for an answer, deepest on top.</Term>
  <Term name="memo">A table of answers already found: memo[k] holds fib(k) once it is known.</Term>
  <Term name="memo hit">A call answered by looking in the memo instead of recursing.</Term>
</Terms>

</Section>

<Section step="see" title="First, without a memo">

Watch plain recursion compute fib(6) and keep an eye on the **calls** row: fib(2) is computed 5 times and fib(1) 8 times.

<Explore slug="fibonacci-memoization" settings={{ preset: 'naive', n: 6 }} caption="25 calls for fib(6). Each extra n multiplies the calls by about 1.6." />

Now the same function with a memo. The first time fib(k) finishes, its answer goes into memo[k]; every later call to
fib(k) returns it at once.

<Explore slug="fibonacci-memoization" settings={{ preset: 'memo', n: 6 }} caption="11 calls for fib(6): each value is computed once and looked up after that." />

<KeyIdea>

The plain version does work proportional to the **number of calls**, which grows like $1.6^n$. The memoised version does
work proportional to the **number of distinct subproblems**, which is just $n + 1$. Memoization pays off whenever a
recursion asks overlapping questions.

</KeyIdea>

</Section>

<Section step="do" title="Turn it around: fill the table bottom-up">

Instead of recursing from the top and remembering on the way back, you can fill the table from the bottom: dp[0], dp[1],
then each dp[i] from the two before it. Same answers, no recursion, no call stack. This is **dynamic programming**: choose
an order in which every value's inputs are already filled in.

<Explore slug="fibonacci-memoization" settings={{ preset: 'table', n: 10 }} input caption="Raise n to 15 and compare: the table needs 14 additions, while plain recursion would make 1,973 calls." />

<Misconception

  title="Memoization makes every recursion fast"

      q: 'You add a memo to merge sort, keyed by the part of the array being sorted. What happens?',

      answer: 1,
      trap: 0,
      why: 'Merge sort splits the array into halves that never overlap, so every call is a new question. A memo is only ever written, never read.',
    },
    {
      q: 'A recursion’s call tree has no repeated labels: every call asks a different question. What will a memo do?',
      choices: ['Turn exponential time into linear', 'Cut the calls roughly in half', 'Use extra memory and save nothing'],
      answer: 2,
      trap: 0,
      why: 'A memo saves work only when a question comes back. With no repeats, nothing is ever looked up.',
    },
  ]}
>

It only helps when the **same** subproblems come back. Merge sort's recursion never repeats a subproblem, so a memo would
just waste memory. Look for overlap first: if the call tree has repeated labels, a memo will help.

</Misconception>

<Misconception
  id="memo-per-call"
  title="A fresh memo in every call"
  probes={[
    {
      q: 'fib(n) starts with memo = {}, then checks memo before recursing and stores its answer at the end. How many calls does fib(6) make?',
      choices: ['11, like the memoised version', '25, the same as with no memo at all', '7, one per value'],
      answer: 1,
      trap: 0,
      why: 'Each call makes its own empty memo, so every look-up misses and every answer is stored where no other call can see it. It does exactly the work of plain recursion: 25 calls.',
    },
    {
      q: 'Where must the memo live, so that later calls can use earlier answers?',
      choices: ['In the deepest call’s frame', 'In a variable made fresh at the start of each call', 'Somewhere every call shares: outside the function, or passed down to each call'],
      answer: 2,
      trap: 1,
      why: 'The point of a memo is that one call writes an answer and another reads it, so all the calls must share one table.',
    },
  ]}
>

The memo has to be **shared** by every call: a variable outside the function, a table passed down to each call, or a
cache decorator such as Python's `@cache`. A memo created inside the function starts empty on every call, so nothing is
ever found and the code is as slow as plain recursion, only with extra work.

</Misconception>

</Section>

<Section step="recap" title="What to remember">

- Memoization = recursion + a table of answers. It turns repeated work into look-ups.
- Cost becomes the number of **distinct** subproblems times the work per subproblem: for Fibonacci, O(n) instead of O(1.6ⁿ).
- Bottom-up dynamic programming fills the same table in a chosen order, without recursion.
- Next: coin change, knapsack and edit distance are all "find the subproblems, then fill the table".

</Section>
