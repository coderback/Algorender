<Section step="hook" title="Socks before shoes">

Your socks and your shirt can go on in either order, but your socks must go on before your shoes. A build is the same:
a library has to be compiled before any program that uses it. Draw each task as a node and each “must come first” as
an arrow, and you have a directed graph.

A **topological order** lists the tasks so that every arrow points forward: each task comes after everything it
depends on. Often many orders work. Sometimes none does: if two tasks each wait for the other, neither can go first.
This lesson finds an order, or proves there isn't one, in time proportional to the size of the graph.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="dependency edge">An edge u → v says u must come before v: v depends on u. A prerequisite points at the course it unlocks.</Term>
  <Term name="topological order">A list of every node in which each edge u → v has u earlier than v.</Term>
  <Term name="in-degree">The number of edges into a node: how many things it waits for. A node with in-degree 0 is ready.</Term>
  <Term name="cycle">A path of edges that comes back to where it started, such as A → B → C → A.</Term>
  <Term name="DAG">A directed acyclic graph: a directed graph with no cycle.</Term>
</Terms>

</Section>

<Section step="see" title="Place whatever waits for nothing">

These are eight courses, from Prg (programming) and Mth (maths) to ML (machine learning). An edge points from a course
to one that needs it: Mth → DS says take maths before data structures. The visualiser runs **Kahn's algorithm**, and
the number beside each node is its in-degree, counting only the prerequisites not yet placed.

<Explore slug="topological-sort" settings={{ preset: 'courses' }} caption="Mth and Prg have no prerequisites, so both start in the queue. Placing Mth lowers Alg and DS to 1; placing Prg brings DS and Sys to 0, so they join the queue. The order comes out Mth, Prg, DS, Sys, Alg, OS, ML, Net, with 9 edges examined, one per edge. Net is the last to become ready: it needs OS too, at the end of the chain Prg → Sys → OS." />

A node can be placed once everything with an edge into it is placed, and Kahn's algorithm keeps that as a count. It
counts each node's in-degree and queues every node whose count is 0. Then, until the queue is empty, it takes the
front node, appends it to the order, and lowers the count of every node it has an edge to. A count that reaches 0
means that node's last prerequisite has just been placed, so it joins the queue.

So every edge points forward, and the queue only decides which ready node goes next. Counting the in-degrees reads
every edge once. After that, each node is queued and taken out once, and each edge is examined once, when the node it
leaves is placed: O(V + E) with adjacency lists (O(V²) with a matrix), and O(V) extra memory for the counts and the
queue.

<KeyIdea>

**A node is ready once everything with an edge into it has been placed. Kahn's algorithm counts each node's unplaced
prerequisites, places ready nodes one at a time, and lowers the counts of the nodes each one points to, queueing any
that reach 0.** Every edge ends up pointing forward, and each node and edge is handled once: O(V + E).

</KeyIdea>

</Section>

leaves it joins the order, so the function returns the list itself. The second print compares the number placed with

The course ml joined the queue on its second edge, not its first: that wait is what separates Kahn's algorithm from
breadth-first search.

An edge from a placed node satisfies **one** prerequisite. A node is ready only when its count reaches 0, when the
**last** edge into it is satisfied. Queueing a node the first time an edge reaches it is what breadth-first
search does, and its order need not be a topological order: with A → B, A → C and C → B, BFS from A visits A, B, C,
though C must come before B. Kahn's algorithm counts down instead, so B waits for C.

</Misconception>

The order code, maths, ml would be just as valid: the program put maths first only because the dictionary lists it
first. That is a tie-break, like the visualiser's first in, first out, not the one right answer.

Two nodes ready at the same moment don't depend on each other, so either can go first. The order is unique only when the queue never holds two nodes, which means each node in the
order has an edge to the next. So a checker can't compare an answer with one expected list; it checks that every edge
points forward.

</Misconception>

Kahn's algorithm has no separate step for cycles. It simply runs out of ready nodes.

<Explore slug="topological-sort" settings={{ preset: 'cycle' }} caption="Only A starts ready. Placing A lowers B to 1 and frees F, which points nowhere. Then the queue is empty with B, C, D and E unplaced: B → C → D → B is a cycle, so none of those three reaches 0, and E waits for D, stuck behind the cycle. 2 of the 6 nodes are placed." />

So the test is a count: fewer than V nodes placed means a cycle. Each stuck node has an edge in from another stuck
node, or its count would have reached 0, so stepping backwards along such edges must come back to a node already
passed: that loop is a cycle. And no list can order a cycle, since whichever of its nodes comes first has an edge into
it from one listed later. **A topological order exists exactly when the graph is a DAG**, and Kahn's algorithm finds
one or proves there is none.

The second O(V + E) method uses [depth-first search](/learn/bfs-dfs). Take any edge u → v as DFS looks at it from u.
If v is undiscovered, DFS(v) runs and finishes before u does. If v has finished, it finished first. If v is still on
the call stack, v reaches u, and the edge closes a cycle. So in a DAG, v always finishes before u: list the nodes as
they finish, then reverse the list.

<Explore slug="depth-first-search" settings={{ input: 'A>B, A>C, B>D, C>D, D>E | start A' }} caption="DFS from A discovers A, B, D, E, and only then C, though C → D: when C looks at D, D has already finished. The nodes finish in the order E, D, B, C, A. Reversed, that is A, C, B, D, E, and every edge points forward." />

Here A reaches every node; in general, start a new DFS from each node not yet discovered, adding to the same list.

DFS discovers a node as soon as any path reaches it, which can be before another node that must come first: above, it
found D through B before it had seen C. Its finishing order is backwards, since each node finishes before everything
that points into it. Only the finishing order **reversed** puts every edge forward. If your edges point the other way,
from a task to what it needs, the finishing order itself is the build order.

</Misconception>

Wherever there are dependencies, there is a topological sort: builds, package installs, a spreadsheet recalculating
each cell after the cells its formula reads, and [backpropagation](/learn/backpropagation), which sends gradients back
through a computation graph in reverse topological order.

<Section step="recap" title="What to remember">

- A topological order lists every node so each edge u → v has u first. One exists exactly when there is no directed
  cycle, and there are often many: ready nodes can go in any order.
- Kahn's algorithm counts in-degrees, queues the nodes with none, then repeatedly places one and lowers the counts of
  the nodes it points to. A node joins the queue when its last prerequisite is placed, not its first. O(V + E).
- Fewer than V nodes placed means a cycle: the rest are on it or stuck behind it.
- DFS works too: reverse the finishing order, not the discovery order. An edge to a node still on the call stack
  means a cycle.
- Next: [strongly connected components](/learn/strongly-connected-components), groups of nodes that can all reach each other; shrink each group to one
  node and what is left is a DAG.
  Practise with [Can Every Course Be Taken?](/practice/course-schedule) and [Course Order](/practice/course-schedule-ii),
  write the DFS way in [Run backpropagation in the right order](/code/topological-backward), or open the
  [topological sort visualiser](/visualisers/topological-sort) and try a graph of your own.

</Section>
