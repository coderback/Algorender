<Section step="hook" title="Binary search you can add to">

[Binary search](/learn/binary-search) finds one key among a million sorted ones in at most 20 probes. Keeping those
keys sorted is the expensive part: an array has to shift every key after the insertion point to make room, half a
million moves for a key that lands in the middle (the [arrays lesson](/learn/arrays) counts them).

A **binary search tree** keeps sorted keys in nodes joined by links instead of side by side. Each node holds one key,
smaller keys go in its left subtree and larger ones in its right, and the same holds at every node below. Finding a key
is binary search again, one comparison per level, and adding one hangs a new node at the bottom without moving anything
else. The catch is the shape: the same seven keys can make a tree 3 levels tall or a chain of 7, and only the order they
arrived in decides which.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="root, child and leaf">The root is the node at the top. Every node has at most two children, a left one and a right one, and a leaf is a node with none.</Term>
  <Term name="subtree">A node together with everything below it. A node's left subtree is its left child and all of that child's descendants, however deep.</Term>
  <Term name="search-tree rule">For every node, every key in its left subtree is smaller than the node's key and every key in its right subtree is larger. Each key is stored once.</Term>
  <Term name="height and depth">Height is the number of levels, counting the root's level as 1: the seven-key tree below has height 3. A node's depth counts the steps down from the root, which has depth 0. (Some books count height in steps instead, which gives one fewer.)</Term>
  <Term name="in-order successor">The next larger key in the tree. When a node has a right subtree, its successor is the smallest key there: go right once, then left as far as possible.</Term>
</Terms>

</Section>

<Section step="see" title="One comparison per level">

This tree holds seven keys. 50 is the root, 30 and 70 are its children, and 20, 40, 60 and 80 are leaves. Search for a
key and watch the path: at each node the search compares, then goes left or right.

<Explore slug="binary-tree" settings={{ start: 'balanced' }} caption="Search for 40, then for 65, then insert 65. 40 is found at the third comparison: 50, 30, then 40. 65 goes right at 50, left at 70 and right at 60, which has no right child, so 65 is not in the tree. Insert 65 walks the same three steps and hangs 65 in that empty spot, as 60's right child." />

When the search for 40 goes left at 50, it rules out 50's whole right subtree, 70, 60 and 80, without looking at them:
every key there is larger than 50, so none of them can be 40. That is binary search again. The subtree the search is
in plays the part of the window, and each comparison throws away everything else. In this tree the root, 50, is even
the middle key, just as binary search probes the middle first.

Insert is a search that is meant to fail. Where the walk falls off the tree is the only place the new key keeps the
rule, so it becomes a new leaf there, and no other node moves. Inserting a key the tree already holds changes nothing.

<KeyIdea>

**Every key in a node's left subtree is smaller than it and every key in its right subtree is larger, so one comparison
rules out a whole subtree.** Search and insert follow a single path down from the root, one comparison per level, so
they cost O(h), where h is the tree's height.

</KeyIdea>

A tree with every level full holds 1, 3, 7, 15 … keys in 1, 2, 3, 4 … levels: $2^h - 1$ keys in h levels. So n keys can
fit in about $\log_2 n$ levels, 20 for a million, the same count as binary search's probes. But the shape is decided by
the order the keys arrive in.

<Explore slug="binary-tree" settings={{ start: 'sorted' }} caption="Seven keys inserted in sorted order, 10 first and 70 last. Each new key was larger than every key before it, so it went right at every node, and the tree is a chain 7 levels tall. Search for 70: it is compared with all seven keys, one per level." />

A chain has height n, so search, insert and delete all cost O(n), no faster than checking a list from the front. Keys
that arrive in random order usually make a tree of height O(log n), a small multiple of $\log_2 n$, but real data often
arrives sorted or nearly sorted: IDs, timestamps, names read from a sorted file. **Self-balancing trees** fix that by
reshaping the tree as keys come and go, so the height stays O(log n) whatever the order.

</Section>

<Section step="do" title="In code, in order, and out of the tree">

In code, a node is a small object: a key and two links, `None` (`null` in JavaScript) where there is no child.
`insert(node, key)` is recursive, like the functions in the [recursion lesson](/learn/recursion): it adds the key
somewhere below `node` and returns the root of that subtree. A call on an empty subtree returns a brand-new node, and
every caller stores what comes back as its child. `search` changes no links, so it never has to come back up the path,
and a loop is enough: it moves `node` to a child until it finds the key or runs out of tree.

  why="insert(root, 40) starts at 50 and, since 40 is smaller, calls insert on 50's left child, 30. 40 is larger than 30, so that call calls insert on 30's right child, which is empty, and this third call makes the node. That is one call per level the walk reached, each waiting for the call it made. Then they return in turn: 30's call stores the new node as its right child, and 50's call stores 30 as its left child again, the child it already had."
/>

The rule also hands you the keys in sorted order. An **in-order traversal** lists a node's left subtree, then the node,
then its right subtree, recursively. Everything on the left is smaller and everything on the right is larger, so if each
subtree comes out sorted, so does the whole list, and each subtree does, by the same argument one level down.

<Explore slug="binary-tree" settings={{ start: 'balanced' }} caption="Run In-order: it finishes 50's left subtree before it visits 50, and the Visited list fills up 20, 30, 40, 50, 60, 70, 80, sorted. Then run Pre-order, which visits each node before its subtrees: 50, 30, 20, 40, 70, 60, 80." />

Listing all n keys this way takes O(n). The smallest key is the leftmost node (keep going left until there is no left
child) and the largest is the rightmost, each O(h) away. That is what a search tree offers over a hash table: the keys in
order, the smallest and largest, and every key between two values.

Deleting depends on how many children the node has. A **leaf** is simply removed. A node with **one child** is replaced
by that child, which brings its whole subtree up with it; every key there was already on the correct side of everything
above. A node with **two children** leaves two subtrees and only one slot, so the node stays and gets a new key instead:
its **in-order successor**, the next larger key. Go right once, then left as far as possible. That key is larger than
everything in the left subtree and smaller than everything else in the right, so the rule still holds. The successor
never has a left child (that child would be smaller still), so taking it out of its old place is one of the two easy
cases.

<Explore slug="binary-tree" settings={{ start: 'balanced' }} caption="Delete 50, then 70, then 20: one of each case. 50 has two children, so its successor, 60 (right to 70, then left to 60), is copied into the root and the old 60 leaf is removed. 70 now has one child, 80, which moves up into its place. 20 is a leaf and is simply removed." />

Each delete is one walk down to the node, and with two children a little further, to the successor: O(h) again. Using
the in-order predecessor instead, the largest key in the left subtree, works just as well; this visualiser uses the
successor.

The rule is about **whole subtrees**: every key anywhere in a node's left subtree is smaller than it, and every key
anywhere in its right subtree is larger. A tree can have each child on the correct side of its parent and still break
it. Put 30 as the left child of 50 and 60 as the right child of 30: 60 is larger than 30, but it sits in 50's left
subtree, and a search for 60 goes right at 50 and never finds it. Checking a tree means passing bounds down: everything
below 30's right must be larger than 30 and also smaller than 50.

Search, insert and delete cost **O(h)**, one comparison per level. h is about log₂ n only when the tree is balanced. A
plain binary search tree keeps whatever shape its inserts give it: sorted input makes a chain with h = n, nearly sorted
input comes close, and then every operation is O(n). The O(log n) guarantee needs a **self-balancing** tree, such as an
AVL or red-black tree, which reshapes itself as keys come and go.

right once, then left as far as possible. The right child is that key only when it has no left child of its own;

left subtree competing for one slot. The successor never has a left child, so taking it out of its old place is a leaf
or one-child removal. The in-order predecessor, the largest key on the left, works just as well.

<Section step="recap" title="What to remember">

- A binary search tree keeps every key in a node's left subtree smaller and every key in its right subtree larger, for
  whole subtrees, not just a node's children.
- Search, insert and delete follow one path down from the root, so they cost O(h). Insert adds a new leaf where a search
  for the key falls off the tree; nothing else moves.
- h is about log₂ n when the tree is balanced (20 levels for a million keys), but n when keys arrive sorted and the tree
  becomes a chain: then every operation is O(n).
- An in-order traversal (left subtree, node, right subtree) visits the keys in sorted order in O(n). The smallest key is
  the leftmost node and the largest the rightmost.
- Deleting a node with two children copies in its in-order successor (right once, then left as far as possible) and
  removes the successor's old node, which has at most one child.
- Next: [self-balancing trees](/learn/balanced-trees), which reshape themselves to keep h O(log n) whatever the order; try sorted inserts on
  the [AVL tree](/visualisers/avl-tree). Practise with [Check a Binary Search Tree](/practice/validate-binary-search-tree),
  [Kth Smallest Value in a Binary Search Tree](/practice/kth-smallest-in-bst) and
  [Lowest Common Ancestor in a Binary Search Tree](/practice/lowest-common-ancestor-bst), write
  [Insert into a binary search tree](/code/bst-insert) and [Write an inorder traversal](/code/inorder-traversal)
  yourself, or open the [binary search tree visualiser](/visualisers/binary-tree) to try more operations.

</Section>
