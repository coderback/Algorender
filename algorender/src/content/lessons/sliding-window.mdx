<Section step="hook" title="The busiest hour in a day of readings">

A sensor takes one reading a second, 86,400 readings a day. Which hour, 3,600 readings in a row, had the highest total?
The obvious way adds up every possible hour: all 82,801 of them, at 3,600 readings each, which is nearly 300 million
additions.

But the hour that starts one second later is almost the same hour. It loses its oldest reading and gains one new one;
the other 3,599 are shared. Keep one running total and update it with just those two readings, and the whole day takes
about 170,000 additions and subtractions.

That is the **sliding window**. Like [two pointers](/learn/two-pointers) it keeps two indices, but instead of closing in
from both ends they move the same way, both to the right, with a running total for the run between them. The same idea
handles windows whose size isn't fixed, such as the longest stretch of text with no repeated letter, and it stays O(n).

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="window">A run of consecutive positions, from a left edge to a right edge. It never skips a position, so it only answers questions about contiguous runs.</Term>
  <Term name="window size k">How many values a fixed window holds. With its right edge at i, it covers positions i − k + 1 to i.</Term>
  <Term name="slide">Move both edges one place right. One value enters on the right and one leaves on the left; the k − 1 in between stay.</Term>
  <Term name="running sum">The total of the values inside the window, kept up to date as the window moves instead of added up again.</Term>
  <Term name="variable window">A window whose size changes: the right edge grows it one value at a time, and the left edge shrinks it when a rule says so, such as while the total is over a limit.</Term>
</Terms>

</Section>

<Section step="see" title="Add one, drop one">

This array holds 4, 2, 12, 3, 8, 1 and 9, and the window holds k = 3 values. The visualiser adds up the first window once,
then slides it right one place at a time, looking for the 3 consecutive values with the largest sum.

<Explore slug="sliding-window" settings={{ input: '4, 2, 12, 3, 8, 1, 9 | k=3' }} caption="The first window, positions 0 to 2, adds up to 18. Each slide adds the value entering and subtracts the one leaving: 18 + 3 − 4 = 17, then 17 + 8 − 2 = 23, the best, at positions 2 to 4. Additions ends at 11: 3 for the first window and 2 for each of the 4 slides." />

Adding every window up again would cost k additions for each of the n − k + 1 windows: O(n·k), and O(n²) when the window
is half as wide as the array. The slide gets the same total with two operations, because the windows before and after
it share k − 1 values. Only the value that left and the value that entered differ, so only those two change the total.

<KeyIdea>

**Keep one running total for the window and update it as the window slides: add the value that enters, subtract the one
that leaves.** The total always equals the sum of the k values inside the window, each slide costs two operations however
wide the window is, and the whole scan is O(n) instead of O(n·k), with O(1) extra space.

</KeyIdea>

</Section>

<Section step="do" title="Wider windows, and windows that change size">

The saving grows with k. A slide costs 2 whatever the width, while re-adding a window costs k.

<Explore slug="sliding-window" settings={{ preset: 'wide', n: 20 }} input caption="A window of 10 over 20 values. Additions ends at 30: 10 for the first window and 2 for each of the 10 slides. Adding up all 11 windows from scratch would take 110. Move the Size slider below to try other sizes: the window stays about half the array, and each slide still costs 2." />

Not every question fixes the size. Say each value is the cost of one day out, and you want the longest run of
consecutive days that costs at most 6 in total. The answer might be two days or five, so the window has to grow and
shrink:

- The **right** edge moves one place every step, adding the new cost to the total.
- While the total is over the limit, the **left** edge moves right, taking costs off, until the window fits again.
- What is left is the longest run ending at the right edge that fits, so compare its length with the best so far.

Dropping the leftmost cost is safe because no cost is negative. A window that is over the limit stays over it however
far right it grows, so no run that fits can start at its left edge any more. The code below runs this on the costs 2, 1,
3, 1, 1, 4 and 2 with a limit of 6.

The same loop solves many window questions; only the rule and what the window keeps change. For the longest stretch of
text with no repeated character, the window keeps a set of the characters inside it, and a repeat entering on the right
makes the left edge move until the earlier copy has left. For the shortest run whose total reaches a target, the left
edge moves while the total still reaches it, recording the length each time.

  id="re-add-each-window"
  title="Each window has to be added up again"

    },
    {
      q: 'A window of 1,000 values slides one place along a list of a million. How many values must be added or subtracted to get its new total?',
      choices: ['1,000', '2', '999'],
      answer: 1,
      trap: 0,
      why: 'One value enters and one leaves; the other 999 are in both windows. Re-adding all 1,000 on every slide would make the scan about a billion additions instead of about 2 million.',
    },

>

Two neighbouring windows share all but two values. The new total is the old total plus the value that entered and minus
the value that left, so a slide costs two operations whatever k is. Adding every window up again costs k for each of the
n − k + 1 windows, O(n·k) in all; the running total makes the scan O(n).

</Misconception>

<Misconception
  id="inner-loop-quadratic"
  title="The while loop inside the for loop makes it O(n²)"
  probes={[
    {
      q: 'A grow-and-shrink window runs over 1,000 values. right steps through all 1,000 positions, and a while loop inside the for loop moves left. In the whole run, at most how many times can left move?',
      choices: ['1,000', '1,000,000', '500,500'],
      answer: 0,
      trap: 1,
      why: 'left only moves right and never passes the end, so it moves at most 1,000 times in total, however those moves are spread over the steps of right. Each value is added once and removed at most once.',
    },
    {
      q: 'What is the running time of the grow-and-shrink window on n values?',
      choices: ['O(n²): there are two nested loops', 'O(n): each value enters once and leaves at most once', 'O(n log n)'],
      answer: 1,
      trap: 0,
      why: 'The inner loop never starts again from the beginning: left carries on from where it stopped. Over the whole run right moves n times and left at most n times, so there are at most 2n updates.',
    },
  ]}
>

Nested loops are O(n²) when the inner loop starts again for every step of the outer one. Here it doesn't: left carries
on from where it stopped and only moves right. Across the whole run right moves n times and left at most n times, so the
window does at most 2n updates: O(n). A step that removes many values uses up removals that later steps can't make, the
same kind of amortised argument as appending to a [doubling array](/learn/arrays).

</Misconception>

      trap: 0,
      why: 'When no value is negative, adding a value never lowers the total, so a window over the limit can only be fixed by moving left. With negative values a later value might fix it, so dropping the left value can lose the answer.',

>

Shrinking from the left relies on one fact: adding a value never lowers the total, so a window that is over the limit
stays over it as it grows. With negative numbers that fails. A value still to come can pull the total back down, and
the window may already have thrown away part of the answer. Questions about runs with negative numbers usually need
prefix sums (the total of everything up to each position) instead, as in
[Count Runs That Sum to k](/practice/subarray-sum-equals-k).

</Misconception>

<Section step="recap" title="What to remember">

- A window is a run of consecutive positions. Keep one running total for it and update it as it moves, instead of adding
  each window up again.
- A fixed window of k values slides one place at a time: add the value that enters, subtract the one that leaves. That is
  two operations per slide, so O(n) instead of O(n·k), with O(1) extra space.
- A variable window grows on the right and shrinks from the left when its rule says so, such as while the total is over
  the limit. Each value enters once and leaves at most once, so it is O(n) too, even with a loop inside a loop.
- Shrinking is only safe when growing can't fix a broken window, as with totals of values that are zero or more. With
  negative numbers, reach for prefix sums instead.
- Next: the **monotonic stack**, which keeps its values in order so each is pushed once and popped at most once (open
  [its visualiser](/visualisers/monotonic-stack)); kept in a deque, the same idea gives the largest value in every
  window in O(n). Practise with [Best Single Trade](/practice/best-time-to-buy-and-sell-stock),
  [Longest Stretch Without a Repeat](/practice/longest-substring-without-repeating) and
  [Longest Run After k Changes](/practice/longest-repeating-character-replacement), then try the hard one,
  [Smallest Window Holding Every Letter](/practice/minimum-window-substring). To try your own values and k, open
  [the sliding window visualiser](/visualisers/sliding-window).
