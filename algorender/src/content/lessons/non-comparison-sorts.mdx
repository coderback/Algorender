<Section step="hook" title="A limit on comparing, and a way round it">

[Merge sort](/learn/merge-sort), [quick sort](/learn/quick-sort) and [heap sort](/learn/heap-sort) take different
routes, but they learn the order the same way: compare two values, act on the answer. However cleverly a sort picks its
comparisons, if comparing is all it does, some list of a million values will cost it at least 18 million of them.
That is a limit on comparing, not on any one algorithm.

Now put 100,000 exam scripts in order of mark, out of 100. No script needs comparing with another. Count how many got
each mark, 101 tallies in all, and the tallies say where each mark goes: if 12 scripts got 0 and 30 got 1, the 2s come
straight after the first 42. One pass to count and one to place is about 200,000 steps, where merge sort makes about
1.5 million comparisons. That is **counting sort**, and **radix sort** stretches it to bigger keys.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="comparison sort">A sort that learns the order only by comparing two elements. Bubble, insertion, merge, quick and heap sort all are.</Term>
  <Term name="lower bound">The fewest steps every algorithm of a kind must take on its worst input.</Term>
  <Term name="key range k">Counting sort needs whole-number keys from 0 to k − 1, such as marks: k possible keys, whether or not they occur.</Term>
  <Term name="running total">Each count plus all the counts before it. Afterwards count[v] says how many keys are v or less.</Term>
  <Term name="stable">Equal keys come out in the order they went in. It matters for records, and radix sort depends on it.</Term>
  <Term name="digit and base">Radix sort writes each key as d digits in base b (base 10 has the digits 0 to 9) and sorts on one digit per pass.</Term>
</Terms>

</Section>

<Section step="see" title="Why comparing has a floor, and counting slips under it">

Start with three different values. They can be in 3! = 6 orders, each needing different moves to put right. A
comparison has two answers, so two comparisons end in at most 4 ways: two of the orders must end the same way, get the
same moves, and one of them comes out wrong. Three comparisons end in up to 8 ways, which is enough.

In general, n different values can be in n! orders, and each comparison at best halves the orders still possible, so
the worst case needs at least ⌈log₂ n!⌉ comparisons. That is a little under n log₂ n: about 18.5 million for a million
values, where merge sort's worst case is about 19 million. In [Comparison budget](/play/comparison-budget) you sort
hidden cards against this bound: 6 cards have 720 orders, so nobody can promise fewer than 10 comparisons.

The bound counts comparisons, so it covers only sorts that compare. Counting sort never does. It uses each key as an
index into a row of counts: one step picks one of k cells, not one of two answers.

<Explore slug="counting-sort" settings={{ input: '3, 0, 4, 1, 3, 1, 4, 3' }} caption="Eight values from 0 to 4. The first pass counts one 0, two 1s, no 2s, three 3s and two 4s. The running totals make those 1, 3, 3, 6 and 8: six values are 3 or less, so the 3s fill positions 3 to 5. Walking from the right, each value goes to its count − 1 and lowers it: the last 3 takes position 5 and the first 3 position 3. Comparisons stays at 0." />

After the running totals, count[v] is how many values are v or less, so the values equal to v end just before
position count[v]. Placing one at count[v] − 1 and lowering the count leaves the slot before it for the next equal
value, so walking from the right puts the last of them last.

Count the work. One pass reads the n values to count them, the running totals visit the k counts, and a second pass
places the n values: O(n + k) time, and O(n + k) memory for the count row and the output row B.

<KeyIdea>

**A comparison learns one yes or no, and n different values can be in n! orders, so a comparison sort needs at least ⌈log₂ n!⌉
comparisons in the worst case, about n log₂ n. Counting sort asks no such questions: it uses each key as an index,
counting in one pass and placing in another, for O(n + k) time and memory with keys from 0 to k − 1.**

</KeyIdea>

</Section>

The bound is about information: a comparison has two answers, so it at best halves the orders still possible. That
binds every sort that learns the order only by comparing, however clever, and nothing else. Counting sort goes from a
key straight to one of k cells. The price is that the keys must be small whole numbers, which a comparison sort never
asks for.

</Misconception>

The trap is how big that price can get: the count row has a cell for every possible key, used or not.

Counting sort pays for every possible key, not just those that occur. With k about n or smaller it is linear; with k
far bigger, the count row is nearly all the work: 10 numbers between 0 and a billion need a billion counts, gigabytes
of memory, where merge sort makes at most 25 comparisons. Keys must also be whole numbers in a known range: negative
ones can be shifted by subtracting the smallest key, but decimals and long strings can't index an array.

</Misconception>

Radix sort keeps the range small by sorting on one digit at a time. Each pass is a stable counting sort with just 10
counts, and the passes go from the ones digit up.

<Explore slug="radix-sort" settings={{ input: '53, 81, 27, 50, 18, 23' }} caption="Six two-digit numbers, so two passes. The ones pass orders them by their last digit, 50 81 53 23 27 18, with 53 still ahead of 23: both end in 3, and 53 came first. The tens pass sorts by the first digit, and numbers that share one keep the order the ones pass left, 23 before 27 and 50 before 53: 18 23 27 50 53 81." />

Each pass costs O(n + 10), one pass per digit of the largest key: d digits in base b cost O(d(n + b)) time and
O(n + b) memory. Numbers below a billion take up to 9 passes over 10 counts, or 3 over 1,000 counts in base 1,000.
With a fixed number of digits, as in 32-bit or 64-bit integers, radix sort is linear in n; fixed-length strings sort
the same way, one character per pass.

A pass looks at one digit and nothing else. Numbers that tie on it keep the order they went in only if the pass is
stable, and that order, from the lower digits, breaks the tie. That is also why the passes start from the least
significant digit: the last pass has the final say, so it must be on the digit that matters most. (Radix sort can
start from the top digit instead, but then it must sort each group of keys separately.)

</Misconception>

<Section step="recap" title="What to remember">

- A comparison sort learns one yes or no per comparison, and n different values have n! orders, so its worst case needs
  at least ⌈log₂ n!⌉ comparisons, a little under n log₂ n.
- Counting sort never compares: count, take running totals, place from the end. O(n + k) time and memory, and stable.
- It pays for every possible key: ideal when k is no bigger than about n, hopeless for a few keys spread up to a billion.
- Radix sort runs a stable counting sort per digit, least significant first: d passes of O(n + b). Stability carries
  the lower digits' order into each pass.
- Next: **bucket sort**, which spreads values over buckets by range and sorts each, linear on average for evenly
  spread values. Practise where counting beats sorting with
  [Same Letters, Different Order](/practice/valid-anagram), [Most Frequent Values](/practice/top-k-frequent-elements)
  and [Group Anagrams](/practice/group-anagrams), play the bound in [Comparison budget](/play/comparison-budget), or open
  the [counting sort](/visualisers/counting-sort) and [radix sort](/visualisers/radix-sort) visualisers.

</Section>
