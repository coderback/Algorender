<Section step="hook" title="Put one value in its place, then split">

[Merge sort](/learn/merge-sort) sorts a million values in at most about 20 million comparisons, whatever their order,
but it needs a buffer as long as the array. The sorts in [sorting in code](/learn/sorting-in-code) need no buffer, but
make up to about n²/2 comparisons: 500 billion for a million values.

**Quick sort** usually gets the best of both. Pick one value, the pivot, and move every smaller value to its left and
every other value to its right. The pivot is now exactly where it belongs, and no value will ever cross it again. Sort
each side the same way and the array is sorted, with nothing to merge and no buffer.

"Usually" is the catch: the speed depends on how evenly the pivots split the values, and the simplest rule, taking the
last value, is at its worst on an already sorted list.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="pivot">The value a partition compares every other value with. This version takes the last value of the part.</Term>
  <Term name="partition">One pass over a part that moves the values smaller than the pivot before it and the rest after it. The pivot ends in its final place.</Term>
  <Term name="boundary i">During a partition, the position where the next smaller value goes. Everything before i is smaller than the pivot.</Term>
  <Term name="in place">Sorting inside the array itself, with a few variables and the call stack as the only extra memory.</Term>
  <Term name="average and worst case">The average is the mean cost over every order of the input; the worst case is the most any input can cost.</Term>
</Terms>

</Section>

A partition walks j along the part once and keeps one boundary, i: values before i are smaller than the pivot, values
from i to j − 1 are at least the pivot, and the rest are unseen. A smaller A[j] swaps into position i and the boundary
moves up one; otherwise j just moves on. Finally the pivot swaps into position i, between the two sides. This is
**Lomuto's partition**; Tony Hoare's original walks two indices in from both ends and swaps less often.

Merge sort splits by position for free and compares afterwards, in the merges. Quick sort does all its comparing
**before** its recursive calls, and afterwards there is nothing left to do: two sorted sides around a pivot already in
place make a sorted part.

A partition of m values compares the other m − 1 with the pivot, once each. If pivots split parts roughly in half, as
45 split 8 values into 4 and 3, each level costs fewer than n comparisons, and there are about log₂ n levels.

<KeyIdea>

**A partition puts the pivot in its final place for m − 1 comparisons. Even splits give about log₂ n levels of fewer
than n comparisons each: O(n log n). If every pivot is the smallest or largest value left, each partition removes only
the pivot, and the comparisons add up to (n − 1) + (n − 2) + … + 1 = n(n − 1)/2: O(n²).**

</KeyIdea>

Pivots don't need to be perfect. A random order mixes good and bad ones, and they average out to O(n log n): about 25
million comparisons for a million values, a third more than merge sort makes. Quick sort usually runs faster anyway:
its inner loop is tiny, and it works within one array, which suits a computer's cache.

A partition sorts nothing but the pivot. It puts each value on the correct side, in whatever order the swaps leave it:
2 4 1 to the left of 6, and 9 7 to its right. So quick sort recurses into both sides until every part holds one value
or none. The pivot's place is final because the values before it are exactly the smaller ones, in any order.

</Misconception>

Those swaps have another side effect: quick sort is not **stable**, since a long swap can carry a value past others
equal to it. In the Predict run, the 45 that started last was the first pivot and landed in position 3, ahead of the
45 that started in position 5. Equal plain numbers can't be told apart, so for them that's harmless: Java sorts arrays
of numbers with a dual-pivot quick sort, but objects with a stable merge sort.

The cost rides on where the pivots land. Here is this version's worst input.

<Explore slug="quick-sort" settings={{ preset: 'sorted', n: 12, seed: 7 }} input caption="12 values in sorted order. Reversed input is as bad, with the pivots alternating between the smallest and largest value left, and so is one value
repeated, since values equal to the pivot all go right. A million sorted values would take about 500 billion
comparisons. The first challenge in [Break it](/play/break-it) runs this quick sort on 10 values you choose: make it
reach its worst, 45 comparisons, where a random order takes about 24.

>

O(n log n) is quick sort's average, not a promise: sorted, reversed and all-equal inputs cost this version about n²/2
comparisons. Real implementations guard against that. A **random pivot** makes the expected cost O(n log n) for any
order of different values, since a long run of unlucky picks is vanishingly rare. **Median-of-three** uses the median
of the first, middle and last values, which splits sorted input evenly, though inputs can still be built to defeat
it. A **three-way partition** gathers values equal to the pivot in the middle and never sorts them again.
**Introsort**, behind std::sort in the common C++ libraries, switches to heap sort wherever the recursion gets too
deep, so its worst case is O(n log n).

</Misconception>

Every move is a swap inside the array, so there is no buffer. But watch depth among the variables: it reaches 11 on
the sorted run and 5 on the Random one.

<Misconception
  id="in-place-no-memory"
  title="In place means quick sort needs no extra memory"
  probes={[
    {
      q: 'A quick sort that takes the last value as pivot sorts 10,000 different values already in order. How deep does its recursion go?',
      choices: ['About 13 calls deep', 'About 10,000 calls deep', 'Not at all: it sorts in place'],
      answer: 1,
      trap: 2,
      why: 'Each partition peels off only the pivot, so each call makes another on a part one value smaller: about 10,000 frames on the call stack at once. Recursive Python code would stop at its default limit of 1,000.',
    },
    {
      q: 'How can a quick sort keep its call stack at O(log n), even when its pivots are bad?',
      choices: ['Recurse into the smaller side, and handle the larger side with a loop', 'Sort in place, which needs no stack', 'Recurse into the larger side first'],
      answer: 0,
      trap: 1,
      why: 'The smaller side holds at most half the values, so each recursive call at least halves its part: at most about log₂ n frames. The loop handles the larger side in the same frame. The time can still be O(n²).',
    },
  ]}
>

In place means no buffer, not no memory: every unfinished call keeps a frame on the call stack. Good pivots make the
recursion O(log n) deep; the worst make it n deep, which can overflow the stack before the O(n²) time even matters. The
fix is to recurse into the **smaller** side and loop on the larger: each recursive call then gets at most half its
caller's values, so the stack holds at most about log₂ n frames.

</Misconception>

<Section step="recap" title="What to remember">

- A partition puts smaller values left of the pivot and the rest right, so the pivot lands in its final place; then
  each side is sorted the same way, with all the comparing before the recursive calls.
- A partition of m values costs m − 1 comparisons. Even splits give about log₂ n levels: O(n log n) on average.
- If every pivot is the smallest or largest value left, as with the last value of a sorted list, the cost is
  n(n − 1)/2 comparisons. Random pivots and median-of-three make that rare; introsort rules it out.
- It sorts in place, but its call stack is O(log n) deep on average and up to n deep at worst; recursing into the
  smaller side caps it at O(log n). It is not stable.
- Next: [heap sort](/learn/heap-sort), which uses a [heap](/learn/heaps) to sort in place in O(n log n) even at worst
  ([its visualiser](/visualisers/heap-sort)), and **quickselect**, which partitions and goes into only the side holding
  the k-th position: O(n) on average. Practise with [Kth Largest Number in a List](/practice/kth-largest-element)
  and [Closest Points to the Origin](/practice/k-closest-points), or make the swaps yourself in
  [Be the algorithm](/play/be-the-algorithm/quick-sort).

</Section>
