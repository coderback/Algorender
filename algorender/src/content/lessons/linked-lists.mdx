<Section step="hook" title="Play next, without the shuffle">

Your music app has a queue of 10,000 songs, and you tap **Play next** on one more. It has to go straight after the song
that is playing. If the queue were an array, every song after that spot would shift one cell along: nearly 10,000 moves
for a single tap.

A **linked list** needs two pointer changes instead. Each song sits in its own node, and each node records where the next
one is, so slotting a song in means changing who points at whom. Nothing moves. The price is what an array gave you for
free: to reach song 5,000, you start at the first and follow 4,999 pointers, one at a time.

Like a stack or a queue, a linked list is cheap at its ends, with one catch you will meet below. Unlike them, it is also
cheap in the middle, as long as you are already standing there.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="node">One element of the list: a value and a pointer to the next node. Each node is its own small allocation, wherever memory had room.</Term>
  <Term name="next pointer and null">A node’s next says where the following node is. The last node’s next is null (None in Python): nothing comes after it.</Term>
  <Term name="head and tail">Pointers to the first and the last node. Everything is reached from head; tail is an extra that makes adding at the back cheap. Both are null in an empty list.</Term>
  <Term name="walk (traversal)">Visiting the nodes in order by following next pointers from head, one hop at a time. It is the only way to reach a node in the middle.</Term>
  <Term name="singly and doubly linked">In a singly linked list each node points only forwards. In a doubly linked list each node also has a prev pointer back to the node before it.</Term>
</Terms>

</Section>

<Section step="see" title="Rewire, don’t shift">

This list holds 7, 23, 42 and 15. Each box is a node, with its value on the left and its next pointer on the right,
where the arrow to the following node leaves. head points at 7, tail at 15, and 15's next is null, drawn as ∅. Insert a
value in the middle, then search for one, and watch the two counts.

<Explore slug="linked-list" settings={{ start: 'example' }} caption="Insert 99 at index 2, then search for 15. The insert visits 2 nodes, 7 and 23, then writes 2 pointers: first 99's next to 42, then 23's next to 99. The search compares 7, 23, 99, 42 and 15, visiting 5 nodes, and finds 15 at index 4." />

Nothing was shifted or copied. 42 and 15 kept their places in memory (the drawing only slides them along at the end, to
make room for 99 in the row), and two arrows changed: the new node took over 23's link to 42, then 23 was pointed at the
new node. That order matters. If 23 pointed at 99 first, nothing would point at 42 any more, and 42 and 15 would be
lost. Linking a node in costs those two writes whether the list has 4 nodes or 4 million.

Getting to the spot is another matter. An array finds index i with one calculation, because its cells sit side by side.
A list's nodes are allocated one at a time, wherever memory had room, so there is no formula for where node i is: the
only way in is head, and the only way along is next. The insert had to walk to 23 before it could link anything, and the
search had to look at every node until it reached 15.

<KeyIdea>

**A linked list rewires instead of shifting. Once you hold the node before the spot, inserting or deleting is one or two
pointer writes: O(1). But nothing says where node i is, so reaching index i, or searching, follows next pointers from
head: O(n).**

</KeyIdea>

The ends are where a list is cheapest. head leads straight to the first node, so inserting or deleting there needs no
walk at all. A **tail** pointer leads straight to the last node, so inserting after it is O(1) too. Deleting the last
node is the exception: it changes the node *before* the tail, and in this list nothing points backwards.

<Explore slug="linked-list" settings={{ start: 'example' }} caption="Insert 8 at the tail, then delete at index 0: neither visits a single node. Then delete at index 3, which now holds the 8: prev has to visit 3 nodes, 23, 42 and 15, to reach the node before the tail, and tail moves back to 15." />

</Section>

<Section step="do" title="Turn a list around, and work its ends">

Reversing a list in place is the classic linked-list exercise, and it shows the one rule of rewiring in its plainest
form: save a link before you overwrite it. The loop keeps three names. prev is the part already turned round (nothing,
at first), cur is the next node to turn, and nxt holds on to the rest of the list. Each pass saves cur's next in nxt,
points cur back at prev, then moves prev and cur one node along.

  answer={1}
  why="The first pass runs `cur.next = prev` while prev is still nothing, so node 1, the old head, becomes the end of the reversed list. Its link to node 2 is gone, which is why the line before saves it in `nxt`: without that, nothing would lead to nodes 2 and 3."
/>

Each pass turns one arrow round and does a fixed amount of work, so reversing n nodes is O(n) time, with three extra
names whatever n is: O(1) extra memory. No value is copied and no node moves; only the arrows change direction.

The loop also shows the right way to go through a list: one pointer, stepped along, visiting each node once. Asking for
positions by index is the wrong way, because each request starts again at head.

>

A list has no address formula. An array finds A[i] at base + i × cellSize because its cells sit side by side, but a
list's nodes were allocated one at a time and can be anywhere, so the only way to node i is from head, following i next
pointers: O(n). A loop that asks for position 0, then 1, then 2 pays that walk every time, which turns an O(n) pass into
O(n²). To visit every node, keep one pointer and step it along, as the reverse loop does.

</Misconception>

The same walk hides inside the O(1) that tables of costs give for inserting into a list.

>

The O(1) is the rewiring, not the finding. Once you hold the node before the spot, linking a new node in is two pointer
writes, however long the list is. Reaching that node by index or by value is a walk from head, so inserting at index i
costs O(i) to get there plus O(1) to link: in the middle of a list that is O(n), the same order as an array's shift. The
real wins are at the head, at the tail with a tail pointer, and right after a node you already have, like the song that
is playing.

</Misconception>

Cheap ends make a linked list a natural **queue**: enqueue inserts at the tail and dequeue deletes at the head, and in
the second list above, neither visited a node. Unlike the ring buffer in [stacks and queues](/learn/stacks-queues), it
never fills up and never has to grow, because each value gets a node of its own. The cost is memory: every value carries
a pointer, 8 bytes on a 64-bit machine, and every node is a separate allocation with its own overhead. Which end does
which job matters, though.

  id="tail-delete-cheap"
  title="A tail pointer makes removing the last node O(1)"
  probes={[
    {

      answer: 1,
      trap: 0,
      why: 'Removing the last node sets the next of the node before it to null and moves tail there. Nodes only point forwards, so finding that node means walking the list from head.',
    },
    {
      q: 'A queue is built on a singly linked list with head and tail pointers. Which way round should it work?',
      choices: ['Enqueue at the head, dequeue at the tail', 'Enqueue at the tail, dequeue at the head', 'Enqueue and dequeue both at the head'],
      answer: 1,
      trap: 0,
      why: 'Adding at either end is O(1), but only the head is O(1) to remove. Dequeuing at the tail would walk the whole list every time. Both at the head would make a stack, not a queue.',

  ]}
>

tail finds the last node in one step, but removing it changes a different node: the one before it, whose next must
become null and where tail must move. Nodes only point forwards, so the only way to find that node is a walk from head,
O(n). That is why a queue on a singly linked list adds at the tail and removes at the head. A **doubly linked list**
keeps a prev pointer in every node, so the node before the tail is one step away and removing at either end is O(1).

</Misconception>

A doubly linked list pays for that with a second pointer in every node, and with twice the pointer writes for each
change: four to link a node in, two to unlink one. In return, any node you hold can be unlinked in O(1), and the list can
be walked in both directions. Java's LinkedList is doubly linked, and Python's collections.deque is a doubly linked list
of blocks of values.

One cost never shows up in big-O. The processor fetches memory in small blocks, so reading one array value brings its
neighbours along for free. A list's nodes can be anywhere, so each hop can be a fresh trip to memory. Walking a list and
scanning an array are both O(n), but the array usually wins by a wide margin, which is why most code reaches for an array
first and keeps linked lists for when it really does splice in the middle.

Linked lists turn up most often as a part inside other structures. A hash table that resolves collisions by chaining,
as Java's HashMap does, keeps the keys that land in one bucket in a short linked list. A graph's adjacency list can keep
each vertex's neighbours in one. An LRU cache keeps its entries in a doubly linked list and finds each entry's node through a hash map, so it can unlink any entry in O(1) (the
[caching lesson](/learn/caching) shows it at work), and a database's B+ tree links its leaves so a range scan can walk
along them (see [storage engines](/learn/storage-engines)).

<Section step="recap" title="What to remember">

- A linked list is a chain of nodes, each a value and a next pointer, reached through head. The nodes can be anywhere in
  memory.
- Inserting or deleting right after a node you hold rewires one or two pointers: O(1). Write the new node's next first,
  so the rest of the list stays reachable.
- Reaching index i, or searching, walks from head: O(n). There is no address formula, and scattered nodes make each hop
  slower than a step along an array.
- head and tail make adding at either end O(1), so a list can back a queue: enqueue at the tail, dequeue at the head.
  Removing the tail is O(n) unless the list is doubly linked.
- Reversing in place turns each arrow round in one pass, saving next before overwriting it: O(n) time, O(1) extra memory.
- Next: [hash tables](/learn/hash-tables), which chain colliding keys in short linked lists, [tries](/learn/tries), where a node can have a next
  pointer for every letter, and [representing graphs](/learn/graph-representations) with adjacency lists. Practise with
  [Reverse a Linked List](/practice/reverse-linked-list) (write it without looking back),
  [Merge Two Sorted Linked Lists](/practice/merge-two-sorted-lists) and
  [Remove the Nth Node from the End](/practice/remove-nth-node-from-end), or open
  [the linked list visualiser](/visualisers/linked-list) to try more operations.
