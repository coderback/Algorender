<Section step="hook" title="How long until it gets warmer?">

A sensor logs the temperature once a minute. For each reading, how long until a warmer one? The direct way scans right
from each reading until it meets something warmer. On a million readings that only fall, every scan runs to the end:
n(n − 1)/2, about 500 billion comparisons. O(n²).

Look at the readings still waiting for an answer. From oldest to newest they never get warmer: a newer, warmer reading
would already have answered the older ones. So a warm reading that arrives beats the newest waiting readings first,
all at one end. Keep them on a [stack](/learn/stacks-queues): each new reading pops every reading it answers, then
waits itself. That is a **monotonic stack**: one pass, each reading pushed once and popped at most once, and fewer than
2 million comparisons for the million readings.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="next greater value">For the value at position i, the first larger value to its right; −1 (or 0 days) if there is none.</Term>
  <Term name="waiting">A position whose answer hasn't been found yet. The waiting positions are exactly the ones on the stack.</Term>
  <Term name="monotonic stack">A stack whose values run one way from bottom to top. For next greater values they never rise: each sits on one at least as large.</Term>
  <Term name="position, not value">The stack holds indices: nums[j] gives the value, j says which answer to fill in, and i − j how long it waited.</Term>
  <Term name="amortised cost">The cost per step averaged over the whole run. One new value can pop many, but every pop uses up a push made earlier.</Term>
</Terms>

</Section>

<Section step="see" title="Pop what the new value beats">

Take seven days of temperatures: 31, 28, 25, 29, 27, 34 and 30. The visualiser walks along them once, with a stack
lane under the array, bottom on the left. Each new value is compared with the top: if the top is smaller, the new value
is its answer and the top is popped; if not, popping stops and the new value is pushed to wait.

<Explore slug="monotonic-stack" settings={{ input: '31, 28, 25, 29, 27, 34, 30' }} caption="28 and 25 wait until 29 arrives and pops both, 25 first; 31 stops it. Then 34 pops 27, 29 and 31, emptying the stack. 34 and 30 are left at the end, so their answers stay −1. Comparisons ends at 10 and Pushes at 7." />

Two facts make this work. A value is pushed only after it has popped everything smaller than it, so it always lands
on something at least as large: the values on the stack never rise from bottom to top. And so the first top that is
not smaller ends the loop, because everything under it is at least as large again.

The stack lane draws values, but the algorithm keeps positions, as its narration says: “Compare 29 with the top of
the stack, 25 (from position 2).”

Now count. Each comparison pops the top or stops the loop, so the 10 comparisons here are 5 pops and 5 stops.

<KeyIdea>

**Keep the positions still waiting for an answer on a stack, whose values never rise from bottom to top. Each new
value pops every waiting value smaller than it, because it is their next greater value, and then waits itself. Each
position is pushed once and popped at most once, so the pass makes fewer than 2n comparisons: O(n), however many one
value pops.**

</KeyIdea>

</Section>

holds positions: `nums[stack[-1]]` is the value on top. It runs on 6, 2, 4, 1, 7 and 3.

Popping j at position i writes answer[j], and i − j is how long j waited, which is all
[Days Until a Warmer Day](/practice/daily-temperatures) asks for. Bare values couldn't say which cell to fill in, how
long it waited, or, when a value repeats, which copy had been beaten.

The comparison is strict: a value pops the top only if it is greater. In the challenge, the second 5 stopped at the
first and waited on top of it, and 7 later popped both.

Greater means strictly greater, so the loop pops only while the top is **less than** the new value. An equal value
stops the popping and waits on top, and both are answered by the next larger value. So equal values sit together, and
the stack never rises rather than strictly falling. If a question wants the next value that is at least as large, pop
on ≤ instead; nothing else changes.

</Misconception>

>

Nested loops are O(n²) when the inner one can take n steps for every step of the outer one. This one can't: each
comparison pops a position or stops the loop. There are fewer than n pops in the whole run, because each position is
pushed once, and at most one stop per value: fewer than 2n comparisons. A value that pops many uses up pops no later
value can make. It is the same amortised argument as appending to a [doubling array](/learn/arrays) or moving the
left edge of a [sliding window](/learn/sliding-window).

</Misconception>

The same loop answers a family of questions; only the comparison, the direction or when you read the stack changes.

- **Next smaller value.** Pop while the top is *larger* than the new value, so the stack rises from bottom to top.
- **Previous greater value.** Pop every value not larger than the new one (≤ this time); the top left behind, if
  any, is the nearest larger value to its left. Read it before the push.
- **A circular list,** where the first value follows the last. Go round twice, reading nums[i mod n] and pushing only
  on the first lap, so values still waiting meet the ones before them. Still O(n).
- **The largest rectangle under a bar chart.** A rectangle as tall as a bar stretches to the nearest lower bar on each
  side, so keep a stack of rising heights. A lower bar arriving is where each taller bar it pops stops on the right,
  the bar under a popped one on the stack is where it stops on the left, and a last bar of height 0 pops the rest.
  In 2, 4, 5, 3, 1, 3, the 1 at position 4 pops the 3 at position 3, whose rectangle runs back to just after the 2 at
  position 0: 3 × 3 = 9, the largest.

The order isn't picked to match the question; it follows from what pops. A new value pops every waiting value it
answers and lands on one it doesn't. For the next greater value it pops smaller values, so the stack falls from bottom
to top: a **decreasing** stack. For the next smaller value it pops larger ones, so the stack rises: an **increasing**
stack. Ask what the new value answers, pop those, and the order takes care of itself.

</Misconception>

<Section step="recap" title="What to remember">

- Scanning right from every value is O(n²). A monotonic stack holds the positions still waiting for a larger value,
  whose values never rise from bottom to top. Each new value pops every smaller one, as their answer, then is pushed.
- Each position is pushed once and popped at most once: fewer than 2n comparisons, O(n) in all and O(1) amortised
  per value, even when one value pops the whole stack.
- Store positions, not values: they say which answer to fill in, and i − j is the distance. Pop on `<` for strictly
  greater, so equal values wait together. Positions left at the end have no answer.
- Flip the comparison for the next smaller value, pop on ≤ and read the top that is left for the previous greater,
  go round twice for a circular list, and keep rising bars for the largest rectangle under a bar chart.
- Next: practise with [Days Until a Warmer Day](/practice/daily-temperatures), then the hard one,
  [Largest Rectangle Under a Bar Chart](/practice/largest-rectangle-in-histogram). A falling stack of bars also solves
  [Rainwater Between Bars](/practice/trapping-rain-water), though two pointers do it in O(1) memory. To try your own
  values, open [the monotonic stack visualiser](/visualisers/monotonic-stack).

</Section>
