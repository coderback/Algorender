<Section step="hook" title="Back to the last junction">

You are in a hedge maze with no map. At each junction you pick a path you haven't tried and walk on. At a dead end you
don't go back to the entrance: you retrace your steps to the most recent junction with an untried path, and take it.
Remember what you have tried and you never explore the same dead end twice.

**Backtracking** builds answers the same way. Make one choice, carry on, and when that branch is finished, with an
answer or at a dead end, undo the choice and try the next. That lists every subset or ordering of a few items, places
queens on a chessboard and fills in a Sudoku. Each choice is a recursive call, and undoing it is the walk back to the
junction.

</Section>

<Section step="parts" title="The pieces you will see">

<Terms>
  <Term name="partial solution">The choices made so far: cur in the subset and ordering visualisers, path in the code, the board in N-Queens.</Term>
  <Term name="choose, explore, un-choose">Add a choice, recurse to make the rest, then remove it so the next choice starts from the same state.</Term>
  <Term name="decision tree">The calls drawn as a tree: each edge is one choice, and each leaf a complete answer or a dead end.</Term>
  <Term name="dead end">A partial solution with no valid next choice: the search backs up to the latest choice with options left.</Term>
  <Term name="pruning">Abandoning a partial solution as soon as it breaks a rule, so nothing below it is ever built.</Term>
</Terms>

</Section>

<Section step="see" title="One choice per level, undone on the way back">

Here is every subset of a, b and c. Each level of the tree decides one item: take it (+) or leave it out (−), and the
search always tries taking first. The cur row holds the partial solution, and a call that has decided all three items
records it.

<Explore slug="subsets" settings={{ preset: 'three' }} caption="The first leaf takes everything, {a, b, c}. Then the call deciding c pops c and leaves it out, recording {a, b}. The empty set, ∅, comes last, once every item has been left out: 8 subsets from 15 calls." />

Watch cur on the un-choose steps: a call that has finished its take branch pops the item it pushed, so the
leave-it-out branch starts from cur exactly as the call found it. The search is depth first: all of
take-a is done before a is ever left out. Each item doubles the leaves, so n items give 2ⁿ subsets.

Orderings make a wider tree. Position 1 can hold any of the n items, position 2 any of the n − 1 still unused, and so on
down to 1, so there are n × (n − 1) × … × 1 = n! leaves. The step is the same: choose an unused item (mark it used and
push it), explore, then un-choose it (pop it and free it) and try the next.

<Explore slug="permutations" settings={{ preset: 'three' }} caption="6 orders from 16 calls: the start, 3 choices for position 1, then 6 calls for position 2 and 6 for position 3. After abc, popping c and then b frees them both, so the loop for position 2 moves on to c, and the next order is acb." />

n! soon outgrows 2ⁿ: 4 items have 16 subsets but 24 orders, and 10 items have 1,024 subsets but 3,628,800 orders.

<KeyIdea>

**Backtracking builds an answer one choice at a time: choose, explore everything that follows, then un-choose, so the
next choice starts from exactly the same state.** The calls form a decision tree with a leaf for every complete answer,
2ⁿ for subsets and n! for orderings. Because every choice is undone, one working list of at most n items and a call
stack about n deep serve the whole search.

</KeyIdea>

This is not [memoization](/learn/memoization): each call here carries a different partial solution, so no question
comes back for a memo to answer. When the same smaller problem does come back, as in counting the subsets with a given
total instead of listing them, use [dynamic programming](/learn/dynamic-programming).

</Section>

A return discards the callee's frame, with its own `i`, and nothing else. `path` is one list that every frame points to,
so whatever a call appends stays until a line removes it, and every later branch sees it. Undo every change a choice
made, right after the call that explored it, the used mark included. (Or pass each call a new list, `path + [x]`:
nothing needs undoing, but every call pays for a copy.)

</Misconception>

Appending `path` stores a reference to the working list, not what it holds right now, so every saved entry is that one
list and changes whenever it does. Save a copy when the answer is complete:
`path[:]` or `list(path)` in Python, `[...path]` or `path.slice()` in JavaScript. Printing a string, as the snippet
does, already makes one.

</Misconception>

In subsets and orderings every leaf is an answer. Most searches aren't like that. Put 4 queens on a 4 × 4 board so that
no two share a row, column or diagonal: of the 4⁴ = 256 boards with one queen per row, only 2 work. A backtracking
solver checks each square before it puts a queen there and rejects any square an earlier queen attacks, so no board
that starts that way is ever built. That is **pruning**.

<Explore slug="n-queens" settings={{ preset: 'four' }} caption="Row 1's queen starts in column 1 and row 2's lands in column 3. Every square of row 3 is then attacked, so the search backs up: row 2's queen slides to column 4. Row 3's queen fits in column 2, but row 4 has no safe square, so row 1's queen moves to column 2. The first solution, columns 2, 4, 1 and 3, comes after 26 squares checked, 8 queens placed and 4 backtracks." />

On the 8 × 8 board, with 8⁸ = 16,777,216 one-per-row boards, the first solution takes 113 placements and 105
backtracks.

Sudoku works the same way: write the smallest digit that fits the first empty cell's row, column and box, and recurse.
When a later cell has no digit left, come back, erase and try the next digit up.

<Explore slug="sudoku-solver" settings={{ preset: 'mini-backtrack' }} caption="12 empty cells. The first dead end comes at row 3, column 4, after 8 digits are written: 1, 2 and 3 are in its row and 4 is in its column. The solver erases back along row 3: column 3 has no other digit, and column 2's next digit, 3, dead-ends too. Only when row 3, column 1 swaps its 1 for a 4 does every later cell fit: 16 digits written and 4 backtracks." />

Pruning is why these finish in a blink. Don't read too much into that.

Pruning skips subtrees that cannot hold an answer, and in a constraint search that is often most of the tree. It
doesn't shrink the tree an input can force. Listing every subset prunes nothing, and a constraint search meets inputs where the rules

exponential. Real solvers prune earlier, say by filling the most constrained cell first, which speeds up typical runs
but leaves that bound alone.

</Misconception>

<Section step="recap" title="What to remember">

- Backtracking builds an answer one choice at a time: choose, explore by recursing, then un-choose, so the next choice
  starts from the same state. The calls form a decision tree, explored depth first.
- Subsets take or leave each item: 2ⁿ leaves. Orderings fill each position from the unused items: n! leaves.
- One working list serves the whole search. A return doesn't undo a choice: pop it (and unmark it). Save a complete
  answer as a copy, never the list itself.
- Pruning rejects a partial solution as soon as it breaks a rule, with its whole subtree: 4 queens take 8 placements,
  not 256 boards. The worst case stays exponential.

  Practise with [All Subsets](/practice/subsets), [All Orderings](/practice/permutations),
